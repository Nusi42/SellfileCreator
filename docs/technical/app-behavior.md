# Application Behavior

This document captures runtime behavior, builder interactions, and user-facing workflows.

## Slot Constraints

- Source of truth: `src/lib/types.ts` exports slot constraints as `ALLOWED_MAIN_BY_SLOT` and `ALLOWED_SUB_BY_SLOT` using `StatVariant` constants (no inline bit-math).
- Helpers: `slotSupportsMain`, `slotSupportsSub`, `anySelectedSlotSupportsMain`, `anySelectedSlotSupportsAllSubstats` centralize feasibility checks.
- Builder integration:
  - `hsfBuilder.ts` calls `anySelectedSlotSupportsMain` before emitting rules so mains that cannot exist on the selected slots are skipped.
  - Substat combinations are not pruned by slot in the builder; this is intentional so RSL can still match rules against Any-slot exports while the UI (Gear Inspector, warnings) surfaces slot feasibility using the shared helpers.
- Rationale: Keeps domain facts in one place so both builder and UI share the same slot feasibility rules and prevents impossible main stats when slots are restricted.

## Builder Outputs and Normalization

- Builder outputs (HSF):
  - Always include `Rank`, `Rarity`, and `Faction` (0 = Any).
  - Always include `ArtifactSet` and `ArtifactType` (emit `[]` when unfiltered).
  - Export order emits `ArtifactSet` (before `ArtifactType`) directly ahead of `Rank` so the legacy `.hsf` diffs stay stable; substat tuples always declare `NotAvailable` before `Condition`.
  - Emits rules only for milestone levels within an explicit window `[minLevel..maxLevel]` (inclusive). Levels are 0/4/8/12/16.
  - Levels where the selected `minCount` substats cannot physically exist for the item’s rarity (e.g., Epic has only 3 substats before +16) are skipped.
  - `Substats` always contains 4 entries (selected + padded).
- SFC normalize: `normalizeRecipe(input: unknown)` builds a `BuilderRecipe` by assembling a base object and conditionally adding optional fields; never assigns `undefined` to optional keys. When `minLevel`/`maxLevel` fields are omitted, the parser defaults the window to `[0..16]` before returning the recipe.
- Aggregate min target: `minRequiredRolls` always applies across the selected substats in a rule. Use `lockedMinRequiredRolls` to enforce an additional locked-only floor (ignored when no substats are locked). When the locked floor is the only aggregate requirement the builder scopes the aggregate sum to just those locked stats; once any global floor exists, both floors apply — the global sum spans every selected stat while the locked sum only considers the locked subset. Legacy SFC files that stored `minRollsTarget: 'Locked'` or `substatMinTarget` are upgraded on import by moving the manual aggregate floor into `lockedMinRequiredRolls`; when locked substats exist the importer now drops the manual total so pure locked-only recipes stay faithful to their original scope.
- Shared normalisation helpers live in `src/lib/recipeNormalization.ts`; the builder UI, SFC IO, and merge path import them so feature rules (keep-mode fallback, auto flex eligibility, rarity supplements, level window guards, etc.) stay consistent everywhere.
- Implementation note: `src/lib/hsfBuilder.ts` now focuses on orchestration while the strongly-typed schema lives in `src/lib/hsfBuilder/types.ts` and roll-target normalization resides in `src/lib/hsfBuilder/targets.ts`. Combination/intro-assignment combinatorics are wasm-owned via `src/lib/wasm/wasmRuleEngine.ts` adapters so builder and rule engine share one implementation.
- Auto-rarity resolution (`resolveAutoRarityCode`) now delegates aggregate/presence/floor selection to the WASM rule engine; TypeScript still applies slot/main compatibility filtering before building the payload.

## Preview Filters (RulesFilterPanel)

- View-only; export is not affected. State lives in `src/lib/rulesFilter.ts`.
- Persistence is mode-aware: Sellfile Preview and Gear Inspector each remember whether the drawer was open, which chips were selected, and which sections were collapsed. Switching modes rehydrates the matching snapshot, and both sets of values persist across sessions.
- Right-click the filter button to open the context menu (same hint overlay as the Export button). The menu includes a persistent “Sync filters between views” checkbox that forces both preview modes to share one filter state, plus a `Reset Filters` action that clears both modes back to factory defaults.
- Shortcut: `Ctrl+F` (`Cmd+F` on macOS) opens the filter panel (when closed) and focuses the recipe-name input if it is present, mirroring the browser “Find” gesture without reusing the native overlay.
- AnyMode chips: `Show` (state `include`) keeps rules that don't specify a field, `Hide` removes them, `Only` shows only those rules.
- Substats support include + exclude in the same button grid:
  - Left click (from Off) toggles “must have”.
  - Right click (from Off) toggles “must not have” (rendered with a diagonal strike on the label).
  - Clicking any active state (left or right) clears back to Off (no cycling between include/exclude).
  - The persisted state stores exclusions in `filter.sub.notSelected` and filtering removes any rule/item that contains any excluded substat variant before evaluating the “must have” match policy.
- Sets
- Metasets unroll into explicit set IDs before matching.
- Match mode `Any`/`All` combines selected sets.
- Final-sell remainder rows (marked internally) are excluded when any set is selected so results aren’t dominated by “All Currently Known”.
- The Sets selector reuses `SetMenuSection` (icons/list) with metaset hover highlights and anchored placement consistent with the Builder.
- Right-click a metaset-derived set entry in any Sets dropdown (Builder, Filters, Safeguards) to mark it excluded; the exclusion clears any explicit include for that set, renders a red indicator in the menu, and chips show excluded set names with strike-through.
- Recipe name regex: the optional field only appears when at least one recipe has a name or the user typed a query. Patterns reuse the builder's styling and accept case-insensitive regex; matching checks recipe names and tag tokens, and invalid input highlights the field but leaves other filters intact. In Gear Inspector mode the match is evaluated against **every** recipe an item matched (`row.matchingRecipeIndices`), not just the winning `match.recipeIdx` — so the same Any-Match semantics as the `Recipe Filter` button apply: an item surfaces when any recipe it matched has a name/tag hitting the query, even if a different recipe won first. The query still ANDs with all other active filter options.
- Recipe buttons: the filter header always shows two controls. `Preview Recipes` (the visibility toggle next to the recipe-name field) hides chips whose rules fail the active filters; it now defaults to off and `Reset filters` returns it to off. `Recipe Filter` gates the preview to the selected recipe chips: in Sellfile mode it’s a simple On/Off toggle, while Gear Inspector mode expands it into a tri-state (`Off` → `First-Match` → `Any-Match`) so users can decide whether the imported gear requires the first matching recipe or any matching recipe. When no chips are selected the button still cycles but effectively behaves like `Off`, and `Reset filters` always returns it to `Off`.
- Collapsible sections keep a builder-style Clear icon next to their collapse toggle. The icon only appears when that section diverges from its defaults (including Gear Inspector-only controls such as glyph chips or the level slider) and clicking it resets just that subset without touching the rest of the filters.
- When the preview switches to the Gear Inspector grid, the `Rule` section becomes a four-button result filter (Keep, Sell, Matched, Unmatched). The Any/Only chips for Slot/Rank/Rarity/Level hide because the gear queue always provides explicit values for those fields. Without Matched, each button is an independent plain filter: Keep shows only keep-tagged items, Sell shows only sell-tagged items, Keep+Sell shows all matched items, Unmatched alone shows only unmatched items. With Matched active (or Unmatched combined with Keep/Sell), the view enters companion context mode: for every sell-tagged item the filter identifies its companions — other gear sharing the same set and slot (plus faction for accessories; set ID 0 gear has no companions) — and renders items at three opacity levels. In Sell focus (Sell active, or Matched alone defaulting to Sell): sell items at 100%, companions at 65%, other group hidden (Matched) or at 25% (Unmatched). In Keep focus (Keep active without Sell): companions at 100%, sell items at 65%, other group hidden or at 25%. Keep+Sell together elevate both sell and companion items to 100%. Companion elevation (65%) only applies when Matched is active; Unmatched without Matched collapses companions to 25% alongside the other group. All four buttons are independent toggles; none are mutually exclusive. State lives in `RulesFilterState.testerResult` as four booleans (`keep`, `sell`, `matched`, `unmatched`); the sanitizer handles backward-compat migration from the legacy Bool3 format. The filter result carries `contextGroupById: Map<number, GearInspectorContextGroup>` when context mode is active, which the grid card uses to set opacity.
- Tester level slider: in Gear Inspector mode the Level section replaces the milestone toggle grid with a compact dual-handle slider (0–16). The handles preserve the existing layout, persist with the rest of the filter state, and filter the gear entries by `artifact.exactLevel` when available (falling back to the milestone level when the exact value is missing). The Sellfile preview keeps the original +0/+4/+8/+12/+16 toggle buttons and their Any chip.
- In Gear Inspector mode both `Recipes` buttons remain visible: `Preview Recipes` continues to control chip visibility, while `Recipe Filter` applies its tri-state filter to those gear entries only (`First-Match` keeps items whose first matching recipe is selected; `Any-Match` keeps items that matched any selected recipe, even if another recipe won first). `Reset filters` always turns `Preview Recipes` back off and returns `Recipe Filter` to `Off`.
- Champion filter: when the queue includes gear equipped on champions (imported collections/vaults/inboxes), a searchable multi-select appears next to the Source buttons so the preview can be narrowed to those heroes’ items. Manually added gear ignores the selector and reappears once the chips are cleared.
- Tester roll filters: the Gear Inspector view still adds a `Rolls` chip next to Substats, but the popover now mirrors the builder’s roll badges instead of comparators. Users either pick counts in the wildcard row (always scoped to “Any stat”) or configure individual stat rows—interacting with one section clears the other so the predicate stays unambiguous. The wildcard row starts empty (matching the chip’s `≥ 0` state) and only lights up once the user toggles badges; selecting every badge auto-collapses back to “≥ 0” so the chip and panel stay in sync. Each row shows the six roll badges (Ø–5) plus a Clear icon to the right of the badge rail (matching the builder’s substat menu). Per-stat rows enforce their own AND semantics, so they no longer modify the Substats picker or Match chip, and they render every rollable stat—including CR% and CDMG%—so testers can filter those substats directly. Summary text and the chip’s aria-label spell out the chosen sets (e.g., `Any rolls {2,4} • SPD {2,4} & ACC {1}`), and clearing the popover removes the filter entirely. When a user selects `5` rolls the matcher also treats Mythical pre-roll bonuses as the hidden fifth roll (the importer exposes them via `mythValue`), so Mythical four-roll substats still satisfy a `5`-roll requirement.
- Gear helpers now live in `src/hooks/useGearInspectorItemsActions.ts`, which assigns deterministic ids, diffs Gear DB imports, and explains every step inline (per the orchestration commenting rules). The hook feeds App.tsx but keeps the signatures stable for future consumers.
- The Gear Inspector pipeline logs `[gear-inspector-items] preview artifacts …` whenever `gearInspectorPreviewArtifacts` rebuilds and `[gear-inspector-items:restore] apply …` when autosave restores rehydrate items. These console stamps confirm when artifact queues are empty, how big the cache is, and whether autosave loads are retriggering Safeguard detection loops.

### Gear Inspector measurements

The default pairing benchmarks `presets/lategame.sfc` against `examples/251112_042110.db`, mirroring the heavy user scenario so regressions show up immediately.

The script echoes base matcher timings, Safeguard candidate/detection durations, emitted Safeguard rule counts, and the matcher timings after those rules are appended so optimizations can be compared without manual instrumentation.
- Rank & Rarity (compact)
  - Side by side on sm+: Rank adapts to content width; Rarity takes remaining space.
  - Condensed controls only (no More/Less): Rank buttons `1★-3★`, `4★`, `5★`, `6★`; Rarity buttons `C/U`, `Rare`, `Epic`, `Legendary`, `Mythical`.
  - Group buttons have explicit click handlers to toggle their member values reliably in multi-select.
- Faction
  - Placed to the right of `Level` in a two-column row (sm+); grouped menu like the Builder. Input width is fixed to avoid layout shift.
- Spacing
  - Chip top margin is centralized: `FILTER_CHIP_TOP_MARGIN` in `src/lib/constants.ts`.
- Empty state
  - When filters hide all rows but rules exist, the table shows: “No RSL Helper Sellfile rules due to the filter.” (prop `emptyDueToFilter`).

## Autosave Restore Dialog

- Hook: `useAutosaveRestore` compares the stored SFC payload (metasets, Substat Target Values, recipes, Final Sell remainder, pinned note, filter state) against the current defaults. When anything differs and the README overlay isn’t blocking, it opens `RestoreAutosaveDialog`.
- Selective restore: Each section appears with its own checkbox (pre-selected). Applying the autosave only touches the checked sections, so builders can import metasets without overwriting recipes, or pull in filters while leaving everything else intact.
- Persistent selections: The dialog persists checkbox states (per section) under `sellfileCreator.autosave.restoreSelection.v1`. The next time the prompt opens, it mirrors the user’s last choices for every available section instead of recomputing defaults, so power users can opt-out of sections once and keep that preference.
- Silent skip: When none of the sections above have anything to restore (e.g., the autosave only contained recipes but the builder already has recipes loaded), App immediately dismisses the dialog instead of flashing an empty shell. This mirrors the pre-dialog UX where no prompt appeared unless there was work to do.
- Filters: The dialog can now restore whether the panel was open, its chips, and collapsed sections; those values live alongside the SFC payload in localStorage.
- Silent preset refresh: When the autosave payload carries a `PresetOrigin` marker (`'beginner'`/`'lategame'`, stamped at save time from the live preset-equivalence match in `sfcPresetMatch.matchedPreset`), `computeInitialAutosaveState` swaps the preset-identity slices of the restore draft — metasets, Substat Target Values, recipes, Final Sell remainder, safeguards, the enabled flags, and the note — for the **current bundled preset** body (`presetDraftFields(variant)`) instead of the stale saved body. Session/override state (filters, sort, override answers, selected indices, grid mode) still comes from the saved payload, so the user's tuning rides on top. This is silent — no UI change, same checkboxes — and mirrors the simple-mode startup behavior so every user picks up preset updates across app versions, not just those launching with `?simple`. SSOT for the preset parse + the swap fields lives in `src/lib/sfcPresetMatch.ts` (`presetDraftFields`, `presetRaw`, `presetFilename`, the `PresetVariant` type), which both the dialog path and `handleLoadSimplePreset` consume. The "is there anything worth restoring" gate still reads the saved note, so a genuinely default session is not forced open by the swap.
- Gear autosave — two separate keys. **Endpoint/imported** gear persists to `AUTOSAVE_GEAR_INSPECTOR_KEY` and is offered as the restore-dialog "Gear Inspector" checkbox (the saved list only replaces current state when the box is checked; once authoritative RSL Helper gear has landed this session, `endpointGearDataApplied` disables the row so a stale draft can't clobber newer data). **Custom ("manual")** gear persists to its OWN key `AUTOSAVE_CUSTOM_GEAR_KEY` — because it's user-authored, RSL Helper never sends it, and endpoint data can never supersede it. Keeping the streams separate is what fixed the "custom gear not saved/reloaded" bug: with a single commingled key, the whole draft was gated behind the endpoint-superseded / dialog-checkbox logic, so manuals silently vanished (and never showed in express/silent mode, which has no dialog). SSOT: `partitionGearInspectorItemsForPersistence` splits live items into the two streams; the live autosave runs two `useAutosave` writers (each with its own compression cache — a shared cache thrashes between the two filtered arrays). The persist-endpoint toggle gates ONLY the endpoint key; custom gear always saves.
- Custom-gear restore is **silent and mode-independent**. `loadCustomGearAutosaveDraft` seeds the manual pieces directly into the initial `gearInspectorItems` state at mount (present from the first render, no dialog, in both express and expert mode), gated only by the per-account "restore custom gear" flag (`getRestoreCustomGearPreferenceSnapshot`, default ON, edited from the account manager dialog below "Save received gear data on this device"). The endpoint restore paths (silent + dialog) then **append** their endpoint draft onto the live items (which already hold the seeded custom gear), de-duplicated by `itemId`, so restoring endpoint gear never wipes customs. Regression coverage: `tests/unit/gear-inspector-persistence-split.test.ts`.
- Dismissal: Dismissing the dialog keeps the previous autosave in storage and delays builder autosave writes until the current session diverges, preventing accidental overwrites. The baseline that "diverges" is measured against is captured at dismissal time, so the *next* change re-enables autosave and overwrites the stored payload — correct when a user dismissed the dialog, wrong when the app dismissed on their behalf and then loaded a document itself.
- **Express boot must not arm divergence (`dismissRestore({ armDivergence: false })`).** In express simple mode App dismisses the restore prompt automatically, and the express startup effect then loads the preset or the saved custom body. Those run in that order, so arming at dismissal would baseline against the still-empty state; the programmatic load would read as a user edit, flip autosave on, and write the loaded body straight over the user's stored document — replacing a custom setup with the bundled preset whenever a `PresetOrigin` marker was present. The express dismissal therefore suppresses arming, and the startup effect calls `rearmAutosaveDivergence()` once its load (including the re-applied override answers) has committed, baselining against the POST-load state. Both halves are required: without the re-arm the express session would never re-enable autosave at all and genuine edits would be lost, which is worse than the overwrite it prevents. `rearmAutosaveDivergence` reads through a layout-effect-synced ref rather than its render closure, because it is invoked from a deferred promise several renders later and the captured scope would still hold the pre-load snapshot.
- Builder autosave now uses `useAutosave({ payloadSignal, buildPayload })`: render passes update only a lightweight change signal, and `buildSfcPayload` runs lazily when the debounced autosave write executes. This keeps large recipe/metaset snapshots off the immediate interaction path.

## Tuple Decoders (HSF → StatVariant)

- `mainToVariant` and `subToVariant` in `src/lib/types.ts` accept either boolean or 0/1 flags for flat/percent and normalize internally. This fixes flat mainstat filtering for inputs that use boolean flags.

## Builder UI

- Builder cheat sheet: The help icon in `BuilderPanel` opens `BuilderCheatSheetPopover`, a scrollable overlay of curated examples for rarity ranges, substat locking/flex, roll targets, and milestone math. The popover reuses the Builder root via `ResizeObserver` so its max height tracks the panel height (capped to 60% of the viewport) and keeps scroll momentum predictable. The popover now renders dedicated sections for `Rolls Cap` (per-rarity roll ceilings with the CDMG cap preview tweaks from `5c24a10`), `Rolls Sum` (examples that show how aggregate targets accumulate and highlight where solo flex rolls appear), and milestone timelines that plot the +0 → +16 stat additions so users can see when a given rarity unlocks each roll opportunity without leaving the cheat sheet.
  The popover renders the same 🔒 aggregate badges the builder uses, so when a recipe reserves Locked Min Required Rolls the cheat sheet shows the lock chip right next to the global badge. Timeline rows animate whenever the builder’s level window changes, keeping the +0 → +16 milestones in sync with the primary panel so screenshots and documentation always show the same roll cadence. Height and scroll momentum reuse the Builder root’s `ResizeObserver`, so wide screens cap at 60% of the viewport while smaller screens borrow the panel’s actual height to avoid double scrollbars.
- Builder helpers: the massive `BuilderPanel` component now keeps shared logic in colocated modules — `src/components/builderPanel/multiEditHelpers.ts` for the multi-edit tri-state/patch reducers, `substatMenuHelpers.ts` for the per-variant roll/target drafts, and `defaults.ts` for the factory builder template. Extend those files (or add new siblings) rather than growing the main component.
- Multi-edit tags: tag edits apply as add/remove patches across the selection. Adding a tag appends it to every selected recipe, removing a tag strips it from every selected recipe, and mixed tags stay visible with the multi-edit mixed styling.
- Recipe overrides preview: the Builder export-mode toggles show the recipe overrides-resolved state. When recipe overrides tags override the stored export mode, a small warning badge (!) appears above the stored toggle (Active/Disabled) to hint what would be selected without the recipe overrides. Clicking the highlighted toggle while the override is active updates the stored selection to match the effective state.
- Gear-set override badge: when a recipe override (`gearsets=` field) changes the effective gear-set selection versus what is stored in the recipe, a `(!)` badge appears above the gear-set MUI select — the same visual language as rank/rarity/export-mode overrides. The `gearsets=+-Name` syntax adds a set as an **excluded** entry (red dashed border in the dropdown) without removing the metaset that originally introduced it; `gearsets=-Name` removes an explicit include. The select's excluded-set red borders always reflect the **effective** (override-resolved) state so the visual matches the HSF output. The select itself remains interactive — edits write to the stored recipe; the override still takes precedence for the exported rules.
- Min-rolls override badge: when a recipe override (`minrolls=` field) changes the effective Global Min Required Rolls (or switches between auto/manual mode), a `(!)` badge appears above the Min Required Rolls button row. The highlighted button and the badge both reflect the **effective** value; the tooltip shows the stored → effective transition. The `@minrolls=N` selector only matches recipes that are already in manual mode (`autoMinRequiredRolls: false`), so auto-mode recipes are unaffected.
- Required-substats override badge: when a recipe override (`minsubstats=` field) changes the effective required substat count (or switches between auto/manual mode), a `(!)` badge appears above the Required Substats button row using the same visual language as the other override badges.
- Override badges are control-anchored, not section-anchored: every override `(!)` marker in both builders lives on the specific control it describes (the select, toggle grid, slider, or per-item chip) *inside* that section's `<Collapse>`. When a section is collapsed the control and its badge unmount together, so a collapsed section deliberately shows **no** override marker — the collapse chevron is never badged. Rationale: the override detail is only actionable while the section is expanded; a user who cares about it will expand the section, and a collapsed-section badge added visual noise without a place to act on it. (This supersedes an earlier chevron-anchored/aggregate approach.) Recipe Builder Level/Mainstat/Substats/Slots anchor their badge to the control inside the Collapse via `renderWarningBadgeOverlay` (a `position:relative` wrapper around the slider/toggle grid); the original bug — a badge pinned *before* the Collapse in a bare relative wrapper that floated detached on collapse — is fixed by keeping the badge inside the Collapse.
- Multi-edit draft sync: `syncMultiEditDraft` only collapses a field to the base draft when there is no patch staged, so patch-based edits (tags, sets, etc.) survive selection changes and undo restores.
- Shared substat toggles: `SubstatToggleDisplay` renders the lock badge, wildcard/min/max indicator, and alignment grid for both the live builder toggles and the cheat sheet snapshots. `substatToggleGroupSx` centralizes the spacing/hover behavior so static rows stay visually identical while interaction hooks remain active only inside the builder. These snapshots intentionally reuse the builder’s lock badge + wildcard glyph component so screenshots in the tutorial, Safeguards dialog, and cheat sheet all show the exact same indicator language.
- Min Required Rolls behavior:
  - Auto, the numeric Global Min Required Rolls (GMRR) buttons, and the Locked Min Required Rolls (LMRR) lock overlay now share one reducer. Auto clears both GMRR and LMR. Clicking a numeric button sets that exact GMRR; clicking it again reverts to Auto and clears any lock.
  - Only one lock can exist. Locking a value greater than or equal to the current GMRR clears the GMRR (while keeping Auto off). Locking a lower value preserves the highlighted number. Unlocking re-highlights the locked number whenever that lock was the only active target.
  - Selecting a numeric value below the current lock clears the lock automatically. Selecting Auto or toggling the last numeric button always clears the lock as well.
  - SFC imports/pastes normalize to these rules (0–5 only, at most one lock, GMRR strictly greater than the lock when both are present).
- `Reset Recipe` button:
  - Left-click: shows a localized confirmation dialog (`builderResetConfirmTitle`) and, when confirmed, resets to user defaults when present; otherwise resets to factory defaults. Buttons reuse shared `cancel`/`reset` catalog entries.
- Right-click (also available on `Insert as recipe` and `Apply as recipe`): opens a shared menu with Save local settings as user defaults, Reset to factory defaults, and toggle checkboxes.
  - User defaults are stored under `sellfileCreator.builder.userDefaults.v1`.
  - Auto reset after Insert: when enabled (default Off), the builder resets to defaults immediately after inserting a recipe (no confirmation dialog). State persists under `sellfileCreator.builder.autoResetAfterInsert.v1`. The toggle disables Auto apply when turned on.
  - Auto apply to selected recipe: when enabled (default Off), builder edits are applied to the current recipe automatically after ~400 ms of inactivity, and pending changes flush before switching recipes or reordering the selected recipe. Preference key `sellfileCreator.builder.autoApplySelectedRecipe.v1`. Enabling this toggle clears Auto reset so the behaviors remain mutually exclusive.
- Numeric spinner adornment: `NumberSpinnerAdornment` (`src/components/NumberSpinnerAdornment.tsx`) is the shared inline spinner used by Builder Roll Targets, the Substat Target Values dialog, and the Gear tab inside the Tools dialog. It traps mouse down events to avoid blurring the active input and keeps the +/- hit targets identical across surfaces so accessibility and pointer behavior stay in sync.
- Recipe name editing keeps a local draft (`BuilderPanel`). Typing updates the draft only; the underlying `BuilderRecipe.name` is updated on blur, on "Add as new/Insert after" and on "Save changes". This prevents in-progress edits from mutating chips/preview while still marking the builder dirty so the save CTA and nudges stay active. Clearing the name routes through the same commit helper.
- Undo/redo history: `useSfcHistory` stores compressed snapshots that include both the SFC payload and the live builder UI state (selection arrays, builder draft, multi-edit draft). Snapshots are keyed by a CRC of the SFC-only signature so UI-only edits refresh the current entry instead of crowding the timeline. Controllers use `describeNextChange(descriptor | null)` to label the next entry, `captureSnapshotNow(descriptor)` to force an immediate append (e.g., before dropping a dirty draft on selection change), `resetHistory(..., { descriptor })` to seed the base entry, and `undoPreview`/`redoPreview` for tooltip metadata without decompressing snapshots.
- Undo/redo tooltips: `BuilderPanel` feeds those previews through `formatHistoryTooltipText` to render the descriptor title plus bullet-prefixed detail lines. When no descriptor is provided the tooltip falls back to the existing i18n copy (which still includes the localized shortcut hint) so localization coverage remains intact.
- Rule count chip: When the selected builder draft doesn't match a cached count, `BuilderPanel` asks the rule cache worker for totals via the `builderCount` message. The worker sums each recipe with `countRulesForRecipes()` and returns the per-recipe counts so the UI only adds them up on the main thread. The hook aborts stale requests and falls back to synchronous counting when Web Workers are unavailable (tests/SSR).
  - Extremely broad recipes can explode into millions of permutations; counting stops once emission exceeds `RULE_COUNT_LIMIT` (~50k) so the UI stays responsive. When the limit trips the chip shows `≥ 50,000 rules` (localized) instead of blocking on an unbounded calculation.
  - Sellfile preview applies a global `TOTAL_RULE_COUNT_LIMIT` (250k) to the combined base HSF and custom builder output. When the cap is hit the offending recipes are omitted from the preview/export (rule chips switch to `≥ 250,000`), while Final Sell remainder rows continue to render so the toggle always reflects user intent.
- Rule cache fast paths:
  - **Pure reorder / delete:** moving recipes (drag, move up/down/top/bottom, “Paste after”) or deleting them no longer enqueues a warm-cache job. The cached rule batches are remapped in place (RecipeID annotations are updated) and the merged preview array is rebuilt from the cached base/custom/final-sell segments.
  - **Final Sell toggles:** changing Final Sell options sends a new pipeline request to the worker; `finalSellRemainder` content is encoded in `lastSentRecipeKey` so if the rules produced are identical (e.g. toggling accessories off when no accessories exist) the structured-clone skip still fires and no large payload crosses the worker boundary.
  - **Worker still required:** inserting recipes or applying the builder to multiple rows continues to flow through the worker. Earlier attempts to splice new batches locally regressed total-limit enforcement and metaset expansion, so the worker remains authoritative for those paths.
  - **Open issues:** Long lists still trigger `[Violation] Forced reflow` due to table virtualization; `HsfRulesTable` still requires follow-up profiling.
  - **Name-only edits:** when the rule fingerprint is unchanged and only recipe names differ, the preview rows update the stored recipe labels in place and skip the worker entirely. Matches and detection remain intact because rule keys did not change.
  - **Restore safety:** autosave restores sometimes surface before deferred snapshots populate; the pipeline now falls back to immediate recipes/metasets/substatTargets to avoid sending an empty payload (which previously yielded final-sell-only previews). A retry guard forces one full warm+match pass if recipes exist but both base and custom rule counts come back zero.
- Worker structured-clone skip: On artifact-only endpoint bursts the worker skips structured-cloning the large rule payload (~50–100 MiB) when `mergedRulesFinal` is provably unchanged, via one `MergedOutputSignature` (`ruleCacheWorker.ts`): `keys` (per-recipe fingerprint strings, compared element-wise so V8 can short-circuit at pointer equality), `recipeKey` (the `composeRuleCacheKey` composite of `substatTargetsKey`, `totalLimitHit`, `truncatedRecipeIndices` identity hash, the merge flags `omitDisabled`/`dedup`, `finalSellRemainder` content, and the safeguard-rule content fingerprint), `detectionKey` (XOR-multiply hash per detection entry covering combination hash, placeholder missing/reason/substat-variant values, and itemKeys), and `mergedCount` (safety net: any rule count change forces a full send regardless of the other three). When the signature matches the last sent one, `rulesByRecipeEntries`, `mergedRules`, and `keys` are sent as `null`; the hook falls back to the most recently received non-null values via `lastRulesRef`. `mergedRulesHash` — the export-dirty fingerprint — is sent on every result regardless, since the export identity must always be current; its ~150 ms crc computation is memoized under the SAME signature (+ the export recipe names), so the shared `MergedOutputSignature` type is the SSOT for what “unchanged merged output” means for both guards.
- **Safeguard rule-content fingerprint SSOT** (`safeguardRulesContentFingerprint` in `lib/safeguards.ts`): the canonical "which fields of a safeguard rule change the generated rules" digest — combination, requiredCount, activation, countMode, ignore flags, substats, **substatMatch**, substatWeights, **weightMainStatByRank**, **mainStatRankWeightFactor**, **improvementChanceThreshold** (excludes display-only `appearance`/`tags`). Both the rule-cache invalidation key (`computeRecipeKey`) and — previously, before the export-output fingerprint replaced it — the export-dirty check consume it, so they agree on what counts as a rule change. Introducing the SSOT fixed a latent bug where the export-dirty digest omitted `substatMatch`/`improvementChanceThreshold`: editing either changed the exported sellfile but left the "needs export/push" badge falsely clean.
- WASM improvement-chance deduplication: `computeImprovementChanceWithLoadedWasm` is called at most once per pipeline run (before detection), and the entries are ALWAYS passed to `evaluateAndCollectSafeguardProtection` via `precomputedImprovementChances` — including threshold-only runs where the caller did not opt into receiving them (previously those runs discarded the result, sent `[]`, and detection recomputed internally: a full double compute). The pass is additionally memoized in the worker under `(safeguard-rule content fingerprint, artifact store fingerprint)` — its exact inputs — so recipe-only edits reuse the previous entries and skip the ~300 ms WASM pass entirely.
- Gate-grouped matcher: `BucketedRules` stores `shared` rules (no slot constraint) once and `per_slot: BTreeMap<i64, RuleBucket>` for slot-specific rules (≈1× input, no clone expansion). Each `RuleBucket` groups its rules by GATE identity (`GateKey`: use/types/sets/faction/rank+rarity masks/level/main-stat — the fields `match_rule_gate` reads) and permutes members so each group is contiguous, with `groups` holding the (start, end) ranges. Rulesets collapse ~13× (33k rules → ~2.5k gate groups on lategame), so `evaluate_item` checks one gate per group and scans member substats only inside passing groups. Because buckets are visited out of flat-list order, "first match wins" resolves as minimum `original_index` per category, and per-recipe decisions carry their match index so encounter order is restored with one sort.
- WASM memory-management internals (talc allocator, engine-gated pre-grow, session-invariant rule caching, worker heap hygiene) are the SSOT of [Build & Tooling](build-and-tooling.md#wasm-linear-memory-management). Behaviorally relevant here: a headless harness running many pipelines back-to-back in ONE process can hit externref-table pressure (`RuntimeError: table index is out of bounds`) — split such work across processes; the in-app worker never runs that densely.
- WASM artifact row store skip: `lastArtifactStoreFingerprint` gates `storeArtifactRows`; when unchanged, `ENGINE_STATE.stored_rows` is reused without JS→WASM serialization. The fingerprint derives from the shared WASM-projection fold (`foldArtifactWasmProjection` in `lib/safeguards.ts` — the SSOT for which artifact fields reach the engine, also used by `computeArtifactSetContentHash`), so every engine-visible field is covered (a substat-variant swap preserving Σ totalValue still invalidates). Both engine-mirroring sentinels (`lastConfiguredKey`, `lastArtifactStoreFingerprint`) reset in the worker's WASM-trap recovery — a fresh instance holds no engine state, so stale sentinels would silently evaluate zero rules.
- Dev tracing: in Vite dev server builds (`import.meta.env.DEV`), `devLog`/`devTimer` emit `[sfc-trace]` lines to both DevTools and the postMessage diagnostic relay (reaches Playwright). All calls compile away to no-ops in production. WASM improvement-chance returns an optional `ImprovementChancePerfDiag` (row/rule/scenario counts) when `debug=true` is passed from the worker.

### Recipe and safeguard rule identity

Recipes and safeguard rules both use **array index** as their runtime identity — neither type carries a persistent `id` field.

**Recipes (`BuilderRecipe`):**
- Selection state is `selectedRecipeIdx: number | null`; multi-select is `selectedRecipeIndices: number[]`.
- Reorder stability: the chips panel tracks selection across reorders via JS object identity (`mapSelectionByIdentity` in `useRecipeSelection`) — the same object reference found at a new index keeps the selection live.
- Autosave restores `SelectedRecipeIndex` with bounds-checking; if the index is out of range the selection falls back to the last recipe.
- Whenever an operation produces a new recipe (builder insert, duplicate, reorder-copy, clipboard paste, tutorial snapshot), call `cloneBuilderRecipe` from `src/lib/multiEditDraft.ts` before writing it into `customRecipes`. Never push shared references — identical payloads must be distinct objects so selection doesn’t sweep every matching recipe.
- When updating an existing recipe (“Apply Builder”), clone the builder draft once and reuse that object for both history descriptors and `setCustomRecipes`. This keeps undo/redo snapshots aligned with the chip identity the selection logic references after the update.

**Safeguard rules (`SafeguardRule`):**
- Selection state is `selectedSafeguardRuleIdx: number | null`; multi-select is `selectedRuleIndices: number[]` managed by `useSafeguardSelection`.
- Reorder stability: same JS object identity approach as recipes (`mapSelectionByIdentity` equivalent inside `useSafeguardSelection.handleRuleReorder`).
- Autosave restores `SelectedSafeguardRuleIdx` with bounds-checking.
- Detection cross-referencing uses `ruleOrdinal` (1-based, matching `__safeguardRuleOrdinal` on injected HSF rows), not a string ID. The Rust engine stamps `ruleOrdinal` on every `SafeguardDetectionEntry`; `build_safeguard_rules_core` matches detection entries to rules by ordinal first, falling back to the legacy `rule_id` field for snapshots produced before this scheme.
- History diffing (`diffSafeguardRules`) uses content-signature-based matching so pure reorders yield `totalChanges = 0` and are correctly recorded as “Reordered” rather than “N rules updated”.

### Rule editing and detection

- The feature is opt-in: the top-level switch mirrors `safeguardsEnabled` and gates both combination editing and detection. When off, detection state is cleared and an info alert explains that scans only run while the toggle is enabled.
- Rules live in the left column. The list uses the shared Gear selectors (`GearMainStatSelect`, `GearFactionSelect`) plus multi-select controls for Slots/Sets/Rank/Rarity/Main Stat so combination filters align with builder affordances. Empty selections map to “Any”, and the Sets dropdown reuses the builder/filter menu so metasets appear at the top (with their glyphs) and stay linked — renaming or editing a metaset updates every Safeguard combination that references it automatically.
- Accessory/artifact selections automatically constrain the set pool and determine whether the faction selector is shown; mixed selections fall back to “all sets”. Faction filters only apply when any accessory slot is included.
- Editing any field updates the builder store immediately. The `≥ required count` input clamps at `1+`, and each card exposes Enable/Disable plus Delete actions.
- Each rule also carries an optional name field directly beneath the enable toggle; names persist through autosave/SFC and logging but do not affect detection or rule generation.
- Three ignore-toggle chips sit alongside the enable switch and refine what the rule counts: `ignorePreviousSafeguards`, `ignoreEquippedInCollection`, `ignoreEquippedInVault`. `ignorePreviousSafeguards` is enforced only on the ranking path (rules with substats selected): when on, the rule drops indices already protected by an earlier active safeguard from its `matching_indices` pool before top-N selection so it reaches deeper into the score ranking instead of redundantly relabeling overlaps. The non-ranking path intentionally ignores the toggle here — its kept-count math (`needed = required − kept_count`) already exposes the toggle's effect by changing how many sold matches the rule reaches for. `ignoreEquippedInCollection` and `ignoreEquippedInVault` remove items equipped on collection/vault champions from each rule's match count so they no longer satisfy that rule's quota. All three default to off.
- The per-rule activation mode has four states: `Off` hides the combination entirely, `Protect existing` mirrors the classic behavior (only emit keep rows for matching gear that would otherwise be sold), `Anticipate gaps` also emits placeholder keep rules whenever the current + sold totals cannot meet the quota so fresh drops stay protected until the inventory export catches up, and `Anticipate improvements` adds an **improvement-chance-gated watch** for quota-satisfied groups: fresh drops stay protected only while they can still clear the rule's improvement-chance threshold. Rules WITHOUT an `improvementChanceThreshold` silently behave exactly like `Anticipate gaps` (the threshold is the mode's brain). Mechanics: detection pushes `missing = 0` placeholders (carrying the group `sample`) only for improvements-mode rules that have a threshold; `improvement_watch.rs` then computes **frontier corners** per (rank × rarity × level 0/4/8/12/16 × size-M focus-substat subset) by probing the improvement-chance engine (`compute_probability` against the rule's challenger scenarios) with synthetic candidates — binary-searching profile lines (balanced + one-lead-per-substat) for the minimal substat values whose chance still meets that level's threshold, rounding thresholds down (keep-biased) and pruning dominated corners. Zero-corner placeholders are dropped (nothing viable clears the bar → normal selling). Perf architecture: the attach pass runs plan → probe → assemble — every group's per-rank challenger set is reduced to its **boundary challenger** (exact: selection depends on the bucket only through the quota-th strongest beats-region; proof at `extract_synthetic_boundaries`), boundary signatures are interned per (rule × slot × main × rank) context, and each boundary-free probe cell is evaluated ONCE for ALL distinct boundaries via a multi-lane recursion leaf (`MultiBoundaryLeaf` — one tree traversal, one f64 lane per boundary, per-lane bit-identical to independent probing; on the reference account 444k (cell × boundary) probes collapse onto 38.5k cells, detection+watch 23.1 s → 16.0 s with an SHA-identical rule set). `safeguard_build_placeholder_rules` emits one HSF rule per corner — pinning `Rank`/`Rarity`/`LVLForCheck` and encoding the corner's per-substat `>=` value thresholds — so RSLH reproduces the threshold decision at every checkpoint of its level-up-then-re-evaluate flow. `missing > 0` (deficit) placeholders emit unchanged in both anticipate modes.
- Required Count is paired with scope chips beneath each picker (everything except `Rank` and `Rarity`). `Per slot`, `Per set`, `Per faction`, and `Per main stat` can be combined to multiply the quota for every Slot × Set × Faction × Main stat tuple; clearing every chip automatically falls back to the shared `Per rule` pool. Inside a **group** the safeguard's Required Count sizes what it feeds the group, and the group keeps its own count out of the merged pool (see [Groups](#groups-safeguards-sharing-one-required-count)).
- The empty state promotes the `Add rule` CTA. Clicking it clones a combination seeded from the slot’s default main stat and set pool; additional clicks append new entries and focus them for editing.
- Detection (`collectSafeguardCandidates` + `computeSafeguardProtection`) only runs when preview gear is present, not building, and the match-freeze gate is released. We derive candidate artifacts by grouping the queue by slot + set + main stat + faction, replaying the merged rules without Safeguards, and keeping only the groups where every artifact would be sold. While a scan is pending the tab shows the warning alert; once complete, each rule keeps a single status chip that reports deficits, “covered elsewhere”, or “satisfied”.
- Recipes flagged `ignoredBySafeguards` still keep items in the preview, but safeguard detection treats those matches as sold so rework fodder does not satisfy uniqueness coverage. This was the `ignore_by_safeguards` tag until v1.0.42; legacy files are transcoded on load (see [Legacy behaviour-tag transcode](rules-and-data.md#legacy-behaviour-tag-transcode)).
- **Tags flyout picker.** Both builder panels offer a picker below the tag input listing every tag NOT yet on the current selection, drawn from recipes **and** safeguards together, so a tag coined on one side is reusable on the other without recalling its spelling. `buildTagVocabulary` (`lib/tagHelpers.ts`) is the SSOT: it normalizes, de-dupes, and sorts. The vocabulary is now purely usage-derived — nothing is seeded, and no tag is privileged, because tags carry no behaviour any more (behaviour lives in the recipe flags below). A fresh document therefore offers nothing until the user coins a tag. Both chip lists in the flyout are bounded in width and height and scroll rather than growing the popover; the flyout width is derived from content (three long-tag chips plus gaps and chrome) instead of a hand-picked number. Coverage: `tests/playwright/builder-tag-picker.spec.ts`.
- **Recipe behaviour flags.** Two explicit recipe fields, surfaced in the builder as a glyph-chip group beside the Tags button (`Flags:` caption, shared `BuilderGlyphToggleChip`, same pattern as the safeguard panel's Ignore chips) and echoed in the recipe chip list as glyphs appended to the Keep/Sell badge:
  - `ignoredBySafeguards` (glyph `⊘`) — this recipe's keeps do not count towards safeguard coverage.
  - `reworkGate` (glyphs `⟳` reworked / `⊙` not reworked) — restricts every emitted rule to one **rework** state (whether a Chaos Ore was applied), via the HSF `Ore` property. Tri-state: absent means the recipe does not care, so the two chips are mutually exclusive by construction rather than by an enforcement rule.
  The two are orthogonal: one changes which gear a rule matches, the other changes whether safeguards count that match. Both were tags until v1.0.42. See [Chaos-ore rule gating](rules-and-data.md#chaos-ore-rule-gating-the-ore-property) and [Legacy behaviour-tag transcode](rules-and-data.md#legacy-behaviour-tag-transcode). Coverage: `tests/playwright/builder-recipe-flags.spec.ts`.
- The rule-cache worker now receives the full safeguard payload (resolved rules + latest detection snapshot) so base rule generation, keep-rule injection, and match-index priming stay off the main thread even when Safeguard mode is enabled.
- **Detection-config invariant:** the worker computes safeguard `base_match` (which gear is "sold", and therefore at-risk) by evaluating each item against the **baseline** ruleset configured into the WASM engine. The engine preserves its configured rules across pushes, and the per-run matcher pass (`buildPipelineMatches`) overwrites them with the **final** ruleset (recipe rules **+ the injected safeguard keep-rules**). So after any matcher pass the worker invalidates its baseline-config sentinel (`invalidateConfiguredKey` in `ruleCacheWorker.ts`), forcing the next run's detection to reconfigure the baseline before computing `base_match`. That baseline reconfigure happens via ONE WASM call — `configureMergedRulesFromComponents` → `merge_cached_and_configure_value` — which finishes the cached merge and builds the engine's `BucketedRules` in place, returning only the merged rule count (`lastConfiguredBaselineCount`; the baseline rules have no TS consumer, so the ~15 MiB serialize-out/expand/minify/serialize-in round-trip is gone). When the configure key already matches, both the merge and configure are skipped and the remembered count feeds the baseline→final index-offset math. Without this, detection runs against the leftover final config, whose injected keep-rules give `ignoredBySafeguards` items (e.g. Chaos Ore "kept for reroll") a non-ignored keep — so they are not flagged at-risk and the safeguard intermittently **under-protects** (a ~285-rule drop on the lategame preset). Regression coverage: `tests/repro/repro-phantom-overprotection.ts` replays a captured endpoint session through the real worker and asserts the protected count stays on its correct high plateau across every build.
- **Candidate-subset matcher (gear-inspector verdict pass):** the final ruleset differs from baseline ONLY by the injected safeguard keep-rules + anticipateGaps placeholders. An item's final gear-inspector verdict can therefore differ from its baseline verdict (from the detection pass's per-item `evaluateResults`) ONLY when a safeguard keep-override can fire for it — i.e. `evaluate_item`'s `allow_keep_override` gate is open, which is the case exactly when the item is **not** already kept by a non-`ignoredBySafeguards` recipe. So the worker re-evaluates only the **candidate subset** — items whose baseline first-match is sold, or kept by an `ignoredBySafeguards` recipe — against the final ruleset, and reuses the baseline verdict for every other item (provably untouched by the injected rules). This replaces the former second full O(N×M) scan. The output is byte-for-byte identical to the full scan (keep/sell **and** the first-match / other-matches presentation are unchanged); the matcher scan shrinks by ~50–90% (≈15–24% of per-push time, account-dependent). The `detectionFoundNothing` path stays as the zero-protected special case; the no-detection path (safeguards inactive) still does a full scan since the final ruleset equals baseline.
- Expected-group expansion for per-scope deficits now runs in the WASM detector using a shared domain payload (slot order, set compatibility pools, allowed mains, and faction ids).
- While detection is pending the Gear Inspector grid keeps the previous Safeguard matches rendered (only for rows whose last `match` came from `RULE_SOURCE_SAFEGUARDS`). We still recompute the base `match`/`baseMatch` metadata immediately, but the visible overlay sticks with the prior Safeguard result so the cards no longer flicker empty → keep → empty → keep during the “apply keep rules” pass.
- Each gear row stores `baseMatch`, the first match result that excludes Safeguard rules. Candidate detection reuses that snapshot instead of replaying `evaluateMatchesByRecipe` for every row, so repeated scans and rule rebuilds no longer stall the UI on large datasets.
- Unique grouping runs even when Safeguards is disabled so the Gear Inspector grid always surfaces the “at risk” combinations; disabling the feature still clears the detection snapshot and hides the deficit chip, but the item list stays populated for browsing.
- The grid header no longer shows a dedicated label; the Filter button anchors to the left while the right edge keeps the detection spinner (when scans are running) immediately before the selection-count chip so the “items” count stays right-aligned with the card column. Deficit summaries now live only inside the rule cards themselves.
- Alerts are contextual: disabled toggle, no gear loaded, or scan pending. Deficit summaries now surface directly on the rule cards, so the header remains dedicated to the filter control and selection count.
- Filter/sort presets (`PreviewHeaderActions.tsx`, right-click the Filter/Sort button) carry an optional **icon** and a **pinned** flag alongside their name/color. The icon is chosen from the shared glyph catalog (`metasetIcons.ts`) via the reusable `GlyphPicker` component (also used by Metasets and the normalized-sort preset editor); the catalog lists colored emoji variants first, then monochrome glyphs, then circled numbers (including a circled-42 easter egg). Pinned presets render as compact icon-only quick-toggle buttons (`PinnedPresetButtons.tsx`) sitting left of the Filter/Sort clear ✕: clicking applies the preset, clicking again while it is the active state clears it (Apply ⇄ Clear). Active detection compares the live state captured as a snapshot against the preset snapshot (`filterPresetSnapshotsEqual` / `sortPresetSnapshotsEqual`); the redundant clear ✕ is hidden whenever a pinned preset is active. The built-in **All Artifacts** / **All Accessories** filter presets and the **Newest** / **SPD** sort presets ship pinned with monochrome glyph defaults. Built-ins persist only the icon/pin **deviations** from their shipped definition (`buildBuiltinIconPinStub` / `resolveBuiltinIconPin` in `presetUtils.ts`), so upgrading users with no stored icon/pin fall through to the new defaults while user-created presets stay unpinned. Built-in stubs whose id no longer exists in the shipped list are dropped on load (`sanitizePreset` returns null), and built-ins **absent** from the stored order are appended at the **end** (`[...stored, ...missing]`), so newly-shipped built-ins land last for existing users without disturbing their saved order/customizations. The Save dialogs default **"include sort/filter" off** and **"pin to header" on** for both filter and sort presets. The pinned-button rows and the Filter/Sort control groups **wrap onto additional lines** when crowded rather than scrolling horizontally.
- Sort popout: the **direction** (asc/desc) and **exclude-glyphs** toggles are enabled throughout Gear Inspector (no longer gated on having priorities/normalized active), so a direction-only or glyphs-only sort preset can be configured and saved. Built-in sort presets include **Ascending** (direction-only) and **Top-Level** (grouping-only: artifacts ungrouped, accessories by faction), both shipped last. A **direction-only** sort still reorders the grid: the grid already shows rows in a natural default order, so `compareGearInspectorPreviewRowsBySubstats` flips that natural order when direction is `asc` (with priorities present the natural order stays a stable tie-breaker). For this to reach the grid, the sort spec is emitted (not nulled) when direction is non-default (`gearInspectorSubstatSortSpec`), the grouping treats a non-default direction as active ordering (`hasSubstatOrdering`), and the Sort button/clear ✕ count it as an active sort.
- **Filter preset apply mode (`exclusive?` on `FilterPreset`).** Filter presets apply in one of two modes. The default (flag absent) is **OR/merge**: applying combines the preset's selections into the current filter instead of replacing it, so the built-ins stack (e.g. pinning **All Artifacts** + **All Accessories** and toggling both shows artifacts *and* accessories). The set-algebra lives in `src/lib/rulesFilterMerge.ts` (`mergeRulesFilterState` / `rulesFilterStateContains` / `subtractRulesFilterState` / `rulesFilterStateHasContribution`) — arrays union, result flags OR, and scalar/object fields are overridden by the preset only where it differs from `DEFAULT_RULES_FILTER_STATE`; the algebra keeps the invariant `contains(b,a) ⟺ merge(b,a) === b` so `subtract` is a clean inverse. Presets are **mode-agnostic**: the snapshot deliberately records no `activeMode`, and applying a preset never switches the active panel. OR apply targets the **currently active filter panel** (Sellfile preview *or* Gear Inspector): `presetPayloadView` (in `rulesFilterMerge.ts`) resolves the preset's meaningful payload — the **active panel's own stored view** when it contributes anything, falling back to the other panel's view otherwise — and merges it into the live panel via the sync-aware `setRulesFilter`/`setFilterCollapsed` (so it fans out to both modes when "sync views" is on). It does **not** touch Sync-views / Limit-recipes / sort. **Active-panel-first resolution is load-bearing:** a snapshot stores one view per preview mode, and with "sync views" **off** each panel keeps its own independent filter, so the two saved views can diverge — the non-active one is then stale leftover state. A mode-agnostic scan (`rules` first, unconditionally) would let that stale rules view win and silently discard the Gear-Inspector selection the user actually configured; with sync **on** both views hold the same state, which is why the bug only ever surfaced with sync off. Regression coverage: `tests/unit/preset-payload-view.test.ts`. A pinned OR preset renders **toggled** iff the current panel's filter already *contains* that payload (per `rulesFilterStateContains`, and only when it actually contributes something; the shared `orPresetActive` helper backs both this and the untoggle below) — so a preset can read as toggled in one panel and not the other. **Cross-panel mapping** lets a preset work in either panel regardless of where it was authored: `projectFilterStateToMode` (in `rulesFilterMerge.ts`) translates the payload onto the active panel before apply/contains/subtract. Shared fields (slots, sets, rank, rarity, level milestones, main/sub, faction, name) pass through; the Keep/Sell intent is mapped between the rules `rule.keep` Bool3 and the Gear-Inspector `gearInspectorResult.keep/sell` (keep-only ↔ 'yes', sell-only ↔ 'no'), so e.g. **Show only Sell** also filters the Sellfile preview as a Sell-rule filter. Pinned presets whose projected payload contributes nothing on the current panel are **disabled** (greyed out) rather than shown lit — gated by `isFilterPresetApplicable` → `rulesFilterStateHasContribution(projectFilterStateToMode(...))`; so a purely Gear-Inspector preset (e.g. sources/matched only, no Keep/Sell or shared field) is disabled in the Sellfile preview, while Sell presets stay enabled there. Untoggling **un-ORs** (`handleUnapplyFilterPreset` in `App.tsx`) by distinguishing two field kinds (tagged `scalar` in `stateMergeAlgebra.ts`): **additive selections** (slot/set arrays, result flags) are pure-subtracted — removed outright — while **shared scalar modes** (every `anyMode`, `sub.match`, etc.) are re-derived from the *other still-active* OR presets (`reapplyRulesFilterScalars`, applying only scalar ops). So untoggling subtracts this preset's selections, then layers the surviving presets' modes back on. This resolves every case without subsumption special-casing: **All Artifacts** + **All Accessories** share only `slots.anyMode: 'off'` (a mode) → restored from the survivor → it stays toggled; **Show only Sell** and **Scoped Sell** share the `sell` flag (a selection) → pure-removed → untoggling *either* clears it and the other reads untoggled. The **exclusive** mode (flag `true`) replaces the whole filter + globals (both panels' views) without switching the active panel; active detection uses exact snapshot equality (`filterPresetSnapshotsEqual`), and untoggling clears the entire filter. All built-ins are OR; new user presets default to OR with an opt-out **"Replace current filter when applied"** checkbox in the Save dialog (`filterPresetsSaveExclusive`). Existing stored user presets (no flag) load as OR.
- **Sort presets stack the same way (`exclusive?` on `SortPreset`).** The generic set-algebra engine lives in `src/lib/stateMergeAlgebra.ts` (shared by filters and sorts); `src/lib/gearInspectorSortMerge.ts` declares the per-field ops for `GearInspectorSubstatSortState`. An OR sort preset **stacks**: its `priorities` are appended to the current sort (deterministic toggle/config order, top-to-bottom, deduped by sort key), while the remaining sort fields (direction, normalized toggles, grouping, weights, exclude-glyphs) follow the shared list-union / scalar-override rules. A pinned sort preset is toggled iff the current sort contains its levels; untoggling subtracts exactly those levels (`handleUnapplySortPreset`). Exclusive sort presets replace the whole sort (legacy) and untoggle clears it. All built-in sort presets are OR; new user sort presets default to OR with a **"Replace current sort when applied"** opt-out (`sortPresetsSaveExclusive`). The optional `filterSnapshot` a sort preset can carry is applied unchanged (it still restores the captured filter when present).
- Generated HSF keep rules are derived from the candidate artifacts instead of the combination filters. For every matching artifact we emit rules across its remaining level milestones (e.g., a +0 item exports 0/4/8/12/16), fix the slot/set/main stat/faction, and encode the current substats as `>=` thresholds so upgrades stay protected. Duplicate artifacts (across overlapping Safeguard filters) are deduplicated by gear id and level milestone to keep the export minimal. When a rule runs in `Anticipate gaps` mode and detection still finds a deficit after counting the sold artifacts, we emit placeholder keep rules that pin the configured slot/set/main/faction filters at `Any level`; these placeholders disappear automatically once the quota is satisfied by real gear. In `Anticipate improvements` mode, quota-satisfied groups additionally emit **watch rules** derived from frontier corners (see the activation-mode bullet above): per rank/rarity/level-milestone/substat-subset, each corner pins `Rank`/`Rarity`/`LVLForCheck` and requires the corner's per-substat `>=` values — the minimal profile whose improvement chance still meets the rule's threshold at that level. The drop-time keep net therefore only covers genuinely promising drops, and the next inventory sync ranks the registered drop normally and releases it if it is not an improvement.
- Substat focus is optional: when a rule selects substats, the match requirement controls how they are enforced. The current model is a minimum count `≥1`–`≥4` (`substatMatch` token `1`–`4`): at least N of the selected substats must be present, with chips above the selection count disabled. `perSubstat` instead applies the quota separately to each selected substat. (Legacy `any`/`all` tokens still load: `any` → `1`, `all` → the selected-substat count.) Matching items are always ranked by the same normalized substat score used in the Gear Inspector (glyphs excluded) and we keep the top N per scope; most would-be score ties are separated first by the epsilon tie-break ladder (unselected useful lines beat flat padding, relevance-aligned flats beat unrelated flats — see the scoring bullet in the WASM section below), and the remaining equal-score ties resolve only when the engine can prove a winner (`same main stat => higher rank`, or `% HP/DEF/ATK beats the matching flat variant`). If a cutoff tie remains unresolved, we keep every boundary-equal item, so the kept count can exceed N. Weights adjust scoring in every min-count mode (`≥1`–`≥4`), while `perSubstat` uses equal weighting. When `Anticipate gaps` emits placeholder rules with substats selected, it outputs one placeholder per substat for the min-count and `perSubstat` modes (each with a `>= 1` guard); a single multi-substat placeholder requiring every selected substat is emitted when the count equals the number of selected substats.
- **Weight by Rank** (`weightMainStatByRank`, chip beside *Per Mainstat*): promotes the existing `same main stat => higher rank` tie-break from an exact-tie-only rule into the score itself, so a 6★ also wins *near*-ties where a same-mainstat 5★ has only slightly better substats. The score gains a main-stat term `SAFEGUARD_MAIN_STAT_RANK_WEIGHT × mainStatRankWeightFactor × (max16[rank] / max16[6★])` for the piece's slot+main-stat, where `max16` is the in-game level-16 main-stat maximum (SSOT `MAIN_STAT_MAX16_BY_RANK_SLOT_VARIANT` in `shared/domain-constants.json`, keyed per **rank+slot+variant** — rarity-independent; banner has higher flat caps and amulet CDMG is half the gauntlet cap, hence the per-slot table; ranks below 4 clamp to 4★). The term is **additive** (it competes alongside the weighted substat sum, never multiplying it) and **level-independent** (it uses the rank's +16 value, not the current level) so leveling a piece never changes its safeguard score, and it is added in every scoring path — detection ranking, live preview, and the improvement-chance candidate **and** challenger projections — so they stay consistent. It contributes only when at least one substat is selected (the chip is disabled otherwise, since the rank tie-break already orders ranks on the no-substat path). New rules default the toggle **ON**; rules loaded from an SFC without the field default **OFF** to preserve their prior scoring. The bundled `lategame.sfc` preset enables it on every safeguard.
- **Mainstat rank weight factor** (`mainStatRankWeightFactor`): a per-rule tunable multiplier on the *Weight by Rank* main-stat term above, so the main stat can be made to compete with (or dominate) the weighted substats. It lives as a first-class weighted row (label *Mainstat (by rank)*) at the top of the substat-weights flyout, alongside the per-substat weight rows; the *Weight by Rank* chip carries a flush tune button (same split-button pattern as the *Improvement chance* chip) that opens the same flyout. The multiplier only applies while the toggle is on (factor `0` neutralizes the term exactly like turning the toggle off; the default `1.0` reproduces pre-factor scoring). Because it is a *dependent* of the toggle, turning *Weight by Rank* off resets the factor back to `1.0` (mirroring how deselecting a substat drops its weight via `normalizeSafeguardSubstatDependents`), and the SFC writer emits it only when the toggle is on **and** the value is non-default — a dormant factor under an off toggle is never persisted. SSOT default/bounds (`SAFEGUARD_MAIN_STAT_RANK_WEIGHT_FACTOR_DEFAULT`/`_MIN`/`_MAX`/`_STEP` = `1 / 0 / 9.9 / 0.1`) live under `mainStatRankWeighting` in `shared/domain-constants.json`; parse/clamp goes through `parseMainStatRankWeightFactor` and the `+/-` control math through `bumpMainStatRankWeightFactor` (both in `lib/safeguards.ts`). It is threaded through the identical scoring paths as the toggle (Rust `safeguard_main_stat_rank_bonus_parts`, the preview `SafeguardWasmScorePreviewIn`, the improvement-chance scenarios), and folded into the rule-content fingerprint + history signature so edits invalidate the cache and mark the sellfile dirty. Autosave (ephemeral session state) keeps the raw value so an in-progress factor survives a reload even with the toggle briefly off; older SFC files without the field load as `1.0`, byte-identical.
- Safeguard rules evaluate against the same candidate pool and do not consume items from earlier rules; a single gear piece can satisfy multiple Safeguard rules, and downstream keep-rule injection dedupe/sort now runs in the WASM rule engine to keep canonicalization + precedence logic single-sourced.
- Safeguard HSF keep-rule generation (artifact level coverage + Anticipate placeholder expansion with substat-match modes) now also runs in the WASM rule engine; `merge.ts` delegates to this binding and no longer keeps a parallel TS implementation of that emit path.
- Substat thresholds in injected Safeguard rules mirror the Gear Inspector’s `subValues` payload (base value plus rolls, excluding glyph bonuses). Using the same numbers keeps glyph-boosted items self-matching in the Gear Inspector grid instead of over-constraining the generated HSF rows.
- The Safeguards grid only renders gear entries that qualify as “unique”: we group artifacts by slot + set + main stat + faction (artifact treats faction as “Any”), replay the active HSF rules with Safeguard combinations removed, and keep the group in view only when every artifact in that group would be sold under that trimmed ruleset. This makes the right-hand grid surface the at-risk combinations that still need protection rules.
- Safeguards uses the keep-override grid column toggle (1 or 2 columns, default 1). The grid pane width is pinned to the Gear Inspector 4-column card width so cards stay identical in both 1- and 2-column modes while the rules pane grows.

### Groups (safeguards sharing one required count)

A **group** is a contiguous run of ordinary safeguards that share one `group.id`. There is no
header entry and no nesting. Every member evaluates exactly as if it were ungrouped — its own
filters, substats, weights, mode, count mode and ranking are all untouched — but a member does not
keep gear itself. It **feeds** the group:

1. Each member selects its top-N exactly as before, where N is **its own required count**. That
   selection is the gear it hands over; nothing else about the member changes.
2. The group pools every member's contribution and **merges** it into buckets keyed by the
   **group's own** `countMode` (its scope chips are the "bucket-defining properties").
3. Within each merged bucket the pool is ranked by the **score each piece got from its own
   member**, and the group keeps **its own required count** — a plain editable number. Everything
   else that was fed is sold.

So two rules feeding 3 and 2 SPD boots keep 5 boots when ungrouped, and however many the group
asks for when grouped. A new group's count is seeded with the MINIMUM of its members' counts (the
tightest promise any of them already made) and its chips with the ones every member already
shares. From then on the count is a plain number — neither the max nor the sum of the members', and
there is no pin/override flag: what the user types is what the group keeps. Setting it above what
the members feed is harmless — a group can only ever keep gear that reached its pool — so to
protect more, raise a member's count as well.

**Ranking uses each member's own score.** Scores are absolute (normalized against canonical max
rolls, never relative to one rule's own pool), so a piece fed by a later member genuinely outranks
a weaker piece fed by an earlier one. Members weighting different substats are therefore compared
on a shared normalization but with their own yardsticks — deliberate, and the reason a member's
weights still matter after it joins a group. Ties break by the member's own rank, then list
order, then item key, so a run is reproducible. Rules with **no** substats score zero across the
board and fall through to list order, exactly as they behaved before groups existed.

**A run publishes only what it KEEPS, and only once it has closed.** Safeguards run
cumulatively — each rule sees earlier rules' picks as already protected, so a later rule does not
redundantly re-protect them. A group is a cap over its members' *finished* selections, so what a
run contributes to that cumulative state is only known after the cap: a piece a member fed but
the group **dropped** is sold, and a later rule must stay free to protect it — exactly as after an
equivalent flat list. Members therefore do not publish inline; their picks are **withheld** until
the run closes, and the close caps first and publishes the survivors
(`safeguard_close_group_run`, before the next rule evaluates). Consequences:

- a rule *after* the group sees exactly the group's *kept* gear as protected — what the cap
  dropped is sold and stays free for a later rule to rescue (`what_the_group_drops_*`); an
  activation-Off member's stale UI `itemKeys` never count as survivors
  (`an_off_members_stale_keys_*`);
- while a run is open nothing writes the cumulative/protected vectors, so every member evaluates
  against the **pre-run** state: its siblings' picks are invisible to it and it ranks the run's
  full pool by its own yardstick (`overlapping_members_*`, `a_members_picks_*`). Note what this
  does **not** change: the ranking path always ranked kept pieces too and emitted only the sold
  ones, so a later member's contribution was always "its top-N minus what a sibling already
  took" — and the cap's first-feeder dedupe (`a_shared_pick_*`) credits it the same way now. What
  moves is a member's own kept/sold split, not what the run keeps;
- `ignorePreviousSafeguards` on a member still means "ignore everything before me": its sold
  view widens to the baseline, and on the ranking path its pool exclusion still counts the run's
  earlier members as "before me" (their pending picks are folded into its view), so it keeps
  reaching *past* its siblings' picks exactly as it did when members published inline
  (`an_ignore_previous_member_*`);
- placeholders (anticipate modes) are cleared only when the group actually turned one of that
  member's fed pieces away — losing a shared piece to an earlier feeder's column is dedupe, not a
  full bucket (`a_pick_credited_to_a_sibling_*`);
- ungrouped lists are untouched: they publish inline as always, and no per-run state is
  allocated for them.

All pinned in `safeguards/group_tests.rs`.

**Settings ride inline on every member — in memory.** `SafeguardRule.group` is
`{ id, requiredCount, countMode }` (`SafeguardGroupSettings`, `lib/safeguards.ts`); every member of
a run carries an identical copy and the run's **first member is the copy the engine reads**. A
single member pasted elsewhere therefore still knows what its group promised. Group ids are opaque
random tokens (`createSafeguardGroupId`), unique only within one array.

**On disk a group is POSITIONAL — identified by shape, not by id.** The `Safeguards` array holds
one entry per group, carrying the settings once plus the `members` it contains:

```
Safeguards: [
  { …rule… },
  { Group: { requiredCount, countMode }, members: [ { …rule… }, { …rule… } ] },
  { …rule… }
]
```

The nesting **is** the grouping, so nothing on disk needs to be unique and **no id is written** —
one is minted per group on load (`normalizeSafeguardGroupSettings`; `grp/<index>` on the Rust
side, which must stay reproducible). Two consequences worth naming: the shape cannot express a
torn or overlapping run, so the reader needs no group repair for anything the writer produced; and
a member's own record gains **no key** from the feature, so a list with no groups re-serializes
byte-identically and a single copied member pastes as an ordinary rule.

`buildReadableSafeguardEntries` / `parseReadableSafeguardEntries` (`lib/sfcIO.ts`) are the one
definition of that projection, shared by the file/autosave path and the clipboard so a run copied
from one document lands as a run in the other; `parse_sfc_safeguard_entries` (`sfc_reader.rs`)
mirrors it for the native DLL. Separators are never nested and never become members. Pinned by
`tests/unit/safeguard-groups-sfc-roundtrip.test.ts` and
`tests/unit/separator-serialization.test.ts`.

**Derived, never stored: which entries form a run.** `resolve_safeguard_groups`
(`wasm/rule_engine_core/src/safeguards/groups.rs`) resolves runs — maximal sequences of ADJACENT
non-separator entries carrying the same id — for the detection scan, the native DLL and the UI
alike; `lib/safeguardGroups.ts` is a memoizing facade over the wasm entry `safeguard_groups_value`.
There is deliberately **no TypeScript re-implementation** (same stance as
`getSafeguardCountKey`/`getSafeguardItemKey`). Membership is "adjacent AND same id", never the id
alone: two stretches with the same id separated by anything are two runs, each capped by its own
head's settings.

**Normalization** (`normalizeSafeguardGroups`, `lib/safeguardGroups.ts`) runs at exactly three
places — the mutation funnel `applySafeguardRulesChange`, the SFC parse path and the
`append`-import seam — and repairs three invariants without ever dropping an entry:
1. an id names one run (a repeated id after a gap keeps the FIRST run's id and re-ids the later
   runs, cloning their settings);
2. a run has at least two members (a group of one is dissolved — it is just a rule with an extra
   count);
3. every member of a run carries the same settings — the canonical copy is the member whose
   settings changed relative to the previous list (found by object identity, since every mutation
   path replaces the edited entry; this is how an edit in the builder's group strip on ONE member
   fans out to its whole run), and the run's head otherwise.

**The two halves of `group` have different owners.** *Membership* (is there a group, and which one
— the `id`) is **structure**: edited only through the chip list (group / ungroup / leave / join /
drag), never from the builder form. *Settings* (`requiredCount`, `countMode`) are edited from the
builder's **group strip** and commit on Apply like any other field.

The draft snapshots `group` when a rule is loaded and nothing resyncs it afterwards, so any seam
that replaces a stored rule with the draft must take membership from the **stored** rule while
letting the draft's settings through. That rebase has one definition,
`withStoredSafeguardMembership` (`lib/safeguardGroups.ts`): the stored side decides *whether* and
*which*, the draft side decides *what it promises*. Used by the builder's apply/auto-apply path —
without it, leaving a group and then pressing Apply wrote the stale draft's `group` straight back
and the rule silently rejoined; dropping the draft's `group` wholesale instead would fix that but
discard the strip's edit with it.

The **dirty check** rebases through the same helper before snapshotting, because it must compare
what Apply would actually WRITE: left raw, the draft's stale `group` reads as a pending change and
lights up an Apply button that then does nothing, staying lit until the rule is reloaded.
`createSafeguardRuleContentSnapshot` keeps carrying `group` — the strip's settings must stay
dirty-detectable; only membership is rebased away. Pinned in
`tests/unit/safeguard-groups-structure.test.ts` and `tests/playwright/safeguard-groups.spec.ts`.

Multi-edit is unaffected by construction — its
`groupRequiredCount` / `groupCountMode` fields no-op on a rule that has no `group`, so it never
creates or restores membership.

**Engine shape.** Members run through the unchanged per-rule evaluation in array order, and
`safeguard_apply_group_cap` runs the moment a run's last member has evaluated (via `safeguard_close_group_run`), pools the members' finished
`item_keys` (each carrying the score from its own member's `candidates`), sorts the pool, keeps the
head's `requiredCount` per bucket keyed by the head's `countMode`, and writes the survivors back
onto the members that fed them — a decision over completed selections rather than an evaluation
of its own. Survivors are re-sorted into each member's own ranked order before being written back,
so rank overlays and preview rows keep the order the member scored them in. Two details matter:

- **Only ACTIVE members feed the pool or consume room.** A member switched Off protects nothing in
  practice; letting its scored keys into the pool would have it silently crowd out its siblings.
- Placeholders are cleared for a member whose contributions were trimmed: once the shared bucket
  is turning real gear away, there is nothing left to anticipate.

A flat list evaluates bit-identically to before groups existed. Detection entries stay in array
order, so `ruleOrdinal === index + 1` continues to hold for every cross-panel consumer.

**From the overrides DSL.** A note can retune a group at session time: `@grouped` / `@ungrouped`
select on membership, and the `group.*` assignment family edits the group's own count and bucket
chips (as opposed to a member's own `count`, which sizes what it feeds the group). Matching any
member writes the whole run, so the members never disagree — see the safeguard-overrides DSL
section below and [note-overrides-editor.md](note-overrides-editor.md#safeguard-groups-in-the-dsl).

**What the four modes mean inside a group** (the builder's mode tooltip gains this paragraph on a
member — `safeguardsGroupModeHint`):

| Mode | In a group |
|---|---|
| **Off** | Feeds nothing, takes no room in the pool. |
| **Protect existing** | Feeds its top-N existing pieces; the group keeps its top-M of the pool. A piece can be *inside this rule's quota yet sold by the group* — the flyout marks such rows in the group's colour ("sold by the group"). |
| **Anticipate gaps** | Also reserves slots for missing drops, but only while the group still has room (see the trimmed-placeholder rule above). |
| **Anticipate improvements** | Watch rules stay computed per member against its own feed and threshold — keep-biased: a drop that beats this member's feed but not the group cutoff is protected until the next sync, then released. |

**Two hand-maintained field lists gate every safeguard mutation, and both must know a new
field.** `applySafeguardRulesChange` drops an update when it produces neither a history
descriptor nor a reorder — the guard that stops empty undo entries. The descriptor is built from
`buildSafeguardRuleSignature` *and compared* by `safeguardRuleSignaturesEqual`
(`history/safeguardsDescriptors.ts`), so a field added to the signature but forgotten in the
comparator compares equal, the change looks like a no-op, and the edit is **silently discarded**.
`group` is in both (compared with `safeguardGroupSettingsEqual`), and in
`safeguardRuleContentFingerprint` (joining/leaving and the group's count/chips all change the
emitted rule set) and `createSafeguardRuleContentSnapshot` (the group strip is a builder edit the
dirty check must see).

**`#` separator prefixes are NOT groups.** They remain a divider line-style hint
(`deriveSeparatorDividerDecoration`). `presets/lategame.sfc` fakes structure with them today
(`Accessories` → `# Rings` / `# Amulets` / `# Banners`); inferring membership on load would silently
turn a divider into a quota-bearing group and change what the file protects. A separator never
carries a group and always ends the run before it.

**Group colour.** Every group is identified by a colour derived from its id
(`lib/labelColors.ts`: FNV-1a hash → golden-angle hue, pushed out of a ±22° band around each of
the active scheme's semantic hues — primary/error/warning/success/info, supplied by
`useReservedLabelHues` — then `ensureContrastOnBg` against the active scheme's paper) — nothing is
stored, and the same helper colours recipe/safeguard **tags** by their text, so a tag reads the same
colour on every chip in all three themes and never looks like a state tint.

**UI.** Member chips carry a coloured left edge (`SAFEGUARD_GROUP_EDGE_PX`, squared where it meets
the neighbouring member so a run reads as one bracket) and, beside their own `Protect ≥ N`, a
`SafeguardGroupBadge` (`⊚ ≥ M` in the group's colour, tooltip naming the group's chips). No chevron,
no collapse, no indentation. The builder form is an ordinary rule form; the **group strip** is butted
against Required Count so the two read as ONE segmented control (like a toggle-button group): the
rule's `Required Count` field, then a `Group`-labelled count field (`⊚ ≥ M`), followed by a
*Buckets:* row of four glyph chips (`KEEP_OVERRIDE_SCOPE_GLYPHS`, the same glyphs the candidate
flyout's cutoff label and group-view chip use; styled exactly like the *Ignore:* chips). Chip
labels come from `KEEP_OVERRIDE_SCOPE_LABEL_KEYS`, the all-false count mode from
`KEEP_OVERRIDE_COUNT_MODE_PER_RULE` and the neutral mixed map from
`KEEP_OVERRIDE_SCOPE_NONE_ACTIVE` — all in `lib/keepOverrideScope.ts` beside the keys and glyphs,
so a fifth bucket dimension cannot be added to some copies and missed by others. Required-count
bounds live once in `lib/safeguards.ts` (`SAFEGUARD_REQUIRED_COUNT_MIN`/`_MAX` +
`clampSafeguardRequiredCount`), shared by the JS clamps, the fields' DOM `max`, and the note
DSL's `count =` clamp, so the input can never accept a value the commit silently rewrites. The
builder stays in the theme's neutral colours — the group colour is the list's job. Always mounted — dimmed and inert on an ungrouped
draft so the row never shifts. Editing the group segments edits the group
(the draft's copy changes; the funnel's normalizer fans it out to the run). In multi-edit the strip
shows whenever any selected rule is grouped and stages `groupRequiredCount` / `groupCountMode` onto
every grouped member (ungrouped ones ignore them — multi-edit never creates a group); with several
groups selected the strip is neutral-coloured and mixed states hatch like every other mixed
control. Context menu: *Create Group* (≥ 2 rules; the block is gathered at its first
member's slot), *Ungroup* (whole run), *Remove from Group* (one member), *Join Group Above/Below*.

**Moves — one rule: a position move never changes membership; only join/leave/drag-into-bracket
do.** `resolveSafeguardDirectionalMove` (all four directional actions, through
`useItemListManager.resolveDirectionalMove`): a selection entirely inside one run moves within it
and stops at the run's edge; anything else is widened to whole units (an ungrouped entry is a unit,
a run is a unit — a partially selected run is taken along in full) and steps over the neighbouring
unit, so an outsider hops a run rather than landing inside it and a run moves as one block.
Drag & drop (`resolveSafeguardDropMembership` + `moveSafeguardEntriesForDrop`, through
`useItemListManager.resolveDropMove` for moves AND Ctrl-copies): the drop guide is inset by
`SAFEGUARD_GROUP_JOIN_OFFSET_PX` and takes the group's colour when the drop will JOIN; a drop point
strictly inside a run always joins, one touching no run never does, and at a run's edge the
pointer's horizontal position decides (the run above wins when both touch the point). A joining drop
gives every dragged rule the run's settings; a flush drop leaves them — except a run dragged IN FULL,
which travels intact (Ctrl-copy of a whole run makes a second group under a fresh id via
`remapSafeguardGroupIds`, so it never merges into its source). Duplicate inserts the clone right
after its source, so a duplicated member stays a member. Paste keeps whatever ids the entries carry;
the normalizer re-ids collisions and dissolves strays.

**Candidate flyout.** On a member, rows inside this rule's own quota that the sell file nevertheless
sells get the group's colour and the "sold by the group" tooltip — but only when no *other* rule
owns the outcome (a final-sell claim is that rule's decision, not a group trim). A *Group* toggle
chip in the flyout header (members only, once detection ran) swaps the list for the pooled **group
view** (`lib/safeguardGroupPool.ts`): every piece the run's members fed, ranked exactly as
`safeguard_apply_group_cap` ranks them, cut at the group's count per group bucket. Built purely
from the members' detection entries (`candidates[].isWithinQuota` = fed, `itemKeys` = survived) —
no second scoring pass.

*Per-row attribution.* The pooled list mixes every member's gear, so each row is attributed to the
member that **fed** it, not to the rule whose flyout is open: `feederByItemKey` carries that
member's ordinal (rendered `·n`) *and* its own `appearance`, and the row's match-source name, that
name's colour, the "this rule matched it" triangle and the primary/de-emphasised row opacity all
resolve from it. Attributing pooled rows to the edited rule printed one member's name beside
another's feeder ordinal and suppressed the triangle on most rows — the opposite of the "why was
my piece kept/sold" question the view exists to answer. Ordinals are list-absolute: entries are
selected *by* `ruleOrdinal` upstream, so an entry without one is dropped rather than folded in
under a run-relative index that would point at an unrelated chip.

**Overrides DSL.** No grammar change. Selectors are tag-based and operate on entries of the same
array, so `@tag=… { count = … }` retunes a member's own count — which is now the size of its
feed. There is no selector or field for the group's own count yet.

**Stored vs effective in the builder form.** `effectiveRule` (`resolveEffectiveSafeguardRule`) is
the rule after note overrides resolve; `rule` is what is stored. The split is deliberate and
consistent: **display** values read `effectiveRule` (so a select, a chip's state, and its override
badge all agree about what is in force), while **dirty flags and clear buttons** read the stored
rule (an override must not make the ✕ that clears a saved value disappear). Scope-chip
*enablement* is display: `redundantDimensions` and `hasAccessorySlot` derive from
`effectiveRule.combination`, so an override that collapses a dimension to one value disables the
chip for it instead of leaving a toggle whose own badge contradicts it. `hasAccessorySlot` is the
single faction-availability predicate for the chip, the faction select and the badge's label
suppression — it must not be re-derived under a second name.

### Safeguards State

- Builder state carries safeguard rules in `safeguardRules` plus the global `safeguardsEnabled` flag. Each gear combination stores `(slot, set, rank, rarity, main stat, faction?)`, optional `substats` + `substatMatch`/`substatWeights` for substat-focused protection, `requiredCount`, and a per-rule activation mode (`off`, `protectExisting`, `anticipateGaps`, or `anticipateImprovements`). Group members additionally carry their inline `group` settings (see [Groups](#groups-safeguards-sharing-one-required-count)); the field is omitted when ungrouped so pre-group files stay byte-identical.
- Autosave and SFC payloads serialize the toggle plus combinations via `Safeguards` and `SafeguardsEnabled`. Autosave restore, clipboard import/export, and history snapshots treat them exactly like recipes/metasets so undo/redo remains accurate. The SFC import path (`applySfcLoadResult`) always writes the file’s safeguard snapshot into state before we trigger a rule cache warm so a file with zero safeguard rules clears the previous session’s entries and lets the preview chip’s progress ring advance cleanly.
- Safeguards history entries emit structured tooltip payloads: add/delete snapshots show the full rule breakdown, while updates render before/after diffs for only the changed fields (slots/sets/metasets/main stats plus rank/rarity/faction lines).
- Safeguard rule names debounce using `BUILDER_AUTO_APPLY_DEBOUNCE_MS`; Gear Inspector match chips refresh from the live name map without forcing a rule-cache rebuild.
- Pipeline requests now carry a monotonic `generation` id; stale in-flight runs are discarded so only the newest payload can update preview state.
- Worker-backed matcher pipelines run through a single-flight scheduler (`useRuleCacheWorker`): one active run, one latest queued payload. New payloads supersede active work immediately.
- Browser builds require worker-backed rule-cache execution; the hook no longer provides a main-thread fallback pipeline.
- `computeSafeguardProtection` / `evaluateAndCollectSafeguardProtection` run entirely in WASM and emit combination stats (`currentCount`, `projectedCount`, `coveredByExisting`, `deficit`, `itemKeys`, scored candidates) that the UI and safeguard-rule generator consume.
- Each present substat contributes its weighted normalized current value **plus** a rank-limited glyph-potential term: glyphs apply at any rank but are capped to the gear's rank tier, so a 6★ outscores an equal-substat 5★ on glyphable stats (CR/CDMG are non-glyphable and add no glyph term — their 5★/6★ order falls to the rank tie-breaker). This per-substat formula is the SSOT `substatNormalizedContribution` in `lib/substatRollNormalization.ts`, shared by the safeguard scorer (`computeSafeguardScoreFromArtifact` + the Rust mirror `safeguard_compute_score`, itself a wrapper over `safeguard_compute_score_for_pass` — see the ranked-slice split below) **and** the Gear Inspector normalized sort (`computeGearInspectorNormalizedSubstatScore`), so both rank mixed-star gear identically. The main-stat rank bonus (`mainStatRankRatio`, gated by the **Weight by Rank** toggle and scaled by `mainStatRankWeightFactor`) is safeguard-only and added after the per-substat sum.
- **Ranked-substat presence gate**: with substats selected but *none of the ones this pass ranks by* present on the piece, the score is exactly `0` — returned before the epsilon ladder and the main-stat rank bonus are added, so those pass-independent terms can never lift such a piece above the `score <= 0` filter every ranking path applies. This is what makes a scoring pass's **membership** a pure function of the ranked substat: on the `perSubstat` path a DEF% pass admits only gear that actually has DEF%. Without the gate, a DEF-main 6★ ring with no DEF% substat scored `1.0` in the DEF% pass (pure main-stat rank bonus), entered the DEF% sub-bucket, and — because weight edits move scores across the `> 0` boundary — made the focused DEF% candidate list *change membership* whenever an unrelated substat's weight was edited, instead of merely re-scoring. The gate is **skipped when the ranked substat could never roll on the piece** — a substat equal to the concrete main stat is impossible, which is exactly why `safeguard_candidate_matches_substats` admits such gear *vacuously*; without that exemption every DEF%-main ring would silently drop out of a `[DEF%]` rule. That possibility check is the `> 0` case of the engine-wide counting rule `safeguard_possible_substat_count` (Rust `safeguard_any_ranked_substat_possible`, TS `anyRankedSubstatPossible`) — the same helper every substat-match gate uses to cap its min-count threshold at what can actually roll on the piece, itself built on the per-variant `safeguard_placeholder_substat_possible` SSOT (TS: `substatMatchesMainVariant`, which is additionally flat-vs-percent aware for HP/ATK/DEF). Mirrored in Rust (`safeguard_compute_score_for_pass`) and TS (`computeSafeguardScoreFromArtifact`); regression tests `per_substat_pass_excludes_gear_without_the_ranked_substat` and `vacuous_ranked_substat_still_scores`.
- **Epsilon tie-break ladder for unselected substats**: on top of the selected-substat sum, every substat *present on the piece* but not selected earns a **fixed per-line** internal tier bonus (SSOT `safeguard.scoring` in `shared/domain-constants.json`) — deliberately **not scaled by roll value**: the epsilon only marks a line's *category*; comparing roll quality is the real weights' job, so equal-category pieces tie exactly and fall to the provable tie-breakers. Tiers: non-flat lines (spd/cr/cdmg/res/acc/%stats) at `SAFEGUARD_SCORE_NON_FLAT_EPSILON_WEIGHT` (`1e-4`); a flat line whose percent twin **is a selected substat** at `SAFEGUARD_SCORE_SELECTED_ALIGNED_FLAT_EPSILON_WEIGHT` (`1e-6`); a flat line whose percent twin is the **piece's own main stat** at `SAFEGUARD_SCORE_MAIN_ALIGNED_FLAT_EPSILON_WEIGHT` (`1e-6`, additive with the previous, so a doubly-aligned flat outranks a singly-aligned one); unrelated flats earn exactly `0`. **The whole ladder is inert on slots whose substat pool has no percent variants — today only the amulet** (`flat HP/ATK/DEF, CDMG, ACC, RES` — demoting flats against percent twins is meaningless where twins can't roll): every amulet line earns `0` and amulets rank purely by selected substats + main-stat bonus, ties falling to the provable tie-breakers. The gate reads the `allowedSubsBySlot` SSOT (Rust `allowed_substats_for_slot`, TS `slotSupportsAnyPercentSubstat` in `lib/types.ts`); unknown slots keep the ladder (conservative armor-like fallback). So when the selected substats tie, pieces with useful remaining lines beat flat padding, and among flat padding a relevance-aligned flat (e.g. flat HP under an HP%-weighted rule or on an HP%-main piece) beats an unrelated one — in every match mode including `perSubstat`, since all scoring paths (detection ranking, preview, per-substat sub-buckets) funnel through `safeguard_compute_score_for_pass` (`safeguard_compute_score` is its single-slice wrapper). **Ranked slice vs rule selection**: `perSubstat` runs one scoring pass per selected substat, so the substats a pass *ranks by* (one variant) are not the substats the *rule selects* (several). The ladder classifies against the **rule's full selection** — `safeguard_compute_score_for_pass(artifact, ranked_substats, rule_substats, …)`, with `safeguard_compute_score` as the wrapper that passes the same slice twice for every non-`perSubstat` caller; the TS mirror takes the same split via `computeSafeguardScoreFromArtifact`'s trailing `ruleSubstats` parameter. Before this split, a `perSubstat` pass saw the rule's *other* picks as unselected padding and paid them epsilons. All tiers sit far below the user weight floor (`0.01`) so stacking can never override an explicit weight edge, carry **no glyph terms**, are gated on a non-empty substat selection (no-substat rules keep their legacy all-zero scoring), and clear `SAFEGUARD_SCORE_TIE_EPSILON` (`1e-9`) so they genuinely decide quota boundaries. Flat classification and the percent↔flat twin lookup are by variant token via one pairs table (`SAFEGUARD_PERCENT_FLAT_PAIRS` powering `safeguard_percent_to_flat_main`/`safeguard_flat_to_percent_substat`; TS `PERCENT_FLAT_SUBSTAT_PAIRS` powering `flatToPercentSubstatVariant`/`isFlatSubstatVariant` in `lib/types.ts`) — **never** the wire `isFlat` flag (SPD/RES/ACC are wire-flat but count as useful non-flat lines). Shared TS helper: `unselectedSubstatEpsilonBonus` (`lib/substatRollNormalization.ts`), applied identically by the safeguard mirror and the Gear Inspector normalized sort. The improvement-chance projections (`compute_projected_challenger_score`, `compute_score_from_state`) intentionally stay epsilon-free on **both** sides of their comparisons — internally consistent, and their quantization grids (thousandth-keys, `WATCH_BOUNDARY_QUANTUM = 0.05`) dwarf these terms.
- `computeMergedRules` prepends Safeguard rules ahead of the Final Sell batch, tagging each rule with `RULE_SOURCE_SAFEGUARDS` and WASM-stamped metadata (combination hash, rule ordinal, required count, scan timestamp). Canonical safeguard-rule keys ensure we skip duplicates when SFC/Final Sell already guarantee the same combination.

## Save/Load Guarantees

- Saver writes `{ Version, Metasets, Minima, Recipes, FinalSellRemainder, SelectedRecipeIndex? }` (via `buildSfcPayload`) and downloads `*.sfc`. When no recipe is explicitly selected, the last recipe index is saved by convention so loaders can preserve intent. Loader compatibility still accepts the legacy `SelectedConfigIndex` key.
- Loader (`readSfcFile`) accepts the readable SFC schema and preserves each merged `substats` entry (`{ stat, fixed?, rollBounds? }`). `substatRollBounds.min`/`max` stay clamped to valid ranges (`min` 0..5, `max` 0..4) and wildcard flags remain intact. Legacy payloads that still provide `fixedSubstats`/`substatRollBounds` are converted inside `sfcIO` so the rest of the app only deals with the new shape.
- Copy All mirrors the saver payload (including `SelectedRecipeIndex`) to enable full round-trip via copy/paste.
- Sellfile export context menu: right-click `Export RSL Helper Sellfile` to open advanced options. `Deduplicate rules` and `Omit disabled rules` persist as in-app rule transforms (keys `sellfileCreator.sellfile.dedupDefault.v1` and `sellfileCreator.sellfile.omitDisabled.v1`) and are applied after base/custom/final-sell generation but before safeguard detection/injection, so preview, matcher, safeguards, downloads, and push exports all share the same transformed ruleset. When the RSL Helper WebSocket endpoint is active, the menu also shows an `Auto-push on change` checkbox (key `sellfileCreator.sellfile.autoPush.v1`, default off): enabling it causes the app to push the sellfile automatically on the rising edge of `hsfDirty` (i.e., whenever edits make the current state diverge from the last export). Auto-push exports suppress the success toast; only failure toasts are shown so background pushes stay unobtrusive.
- Export/push queueing: if a rule-cache pipeline rebuild is pending/running (debounce window or active worker run), export actions are queued and executed once the worker is idle so downloaded/pushed sellfiles match the latest edits. The queue carries the caller's toast intent (`'loud'` for manual exports, `'silent'` for auto-push) so the correct toast behavior is preserved even when the export is deferred.
- **HSF export-dirty (`hsfDirty`) = the exported file would actually differ from the last export.** It is a crc32 fingerprint of the *exact bytes* `buildHsfFileFromMerged(mergedRules, { recipeNames })` would produce, compared against the fingerprint captured at the last export/push (reset to baseline on SFC load/import/restore). The fingerprint is computed by the SSOT helper `computeExportedHsfFingerprint` (`lib/hsfIO.ts`) **in the rule-cache worker** (it already holds the merged rules) and returned as `mergedRulesHash` on every pipeline result; the main thread just compares the string (it does not recompute the crc). The recipe **names** written into the export — one of the crc inputs — are derived on both sides by the single SSOT helper `recipeNamesForExport` (`lib/ruleCacheHelpers.ts`) over the **override-applied** recipe list (`recipesForRuleBuild(applyRecipeOverrides(...))`), not the raw `customRecipes` used for display/match labels. This guarantees the worker's fingerprint and the main thread's actual export payload (`buildExportPayload` → `exportRecipeNames`) agree byte-for-byte even if a future recipe override renames a recipe. Because `cleanHsfForExport` strips every volatile field first (`__safeguardScanMs` timestamp, `projected`/`deficit`/`itemKey`, `__lineIdx`, detection internals), the fingerprint is content-pure: a gear-DB update that doesn't change the injected rules produces the **same** fingerprint (no false "needs export"), and an add-then-remove inventory round-trip returns it to the baseline (correctly goes clean again).
- **Content-keyed pipeline result cache (add-then-remove farming round-trips skip recompute).** The main-thread pipeline LRU (`pipelineCacheRef`, `PIPELINE_CACHE_MAX`/`PIPELINE_CACHE_TTL_MS` in `App.tsx`) keys each cached result on an *artifact-content* hash, `:a${artifactContentHash}:`, where `artifactContentHash = computeArtifactSetContentHash(gearInspectorPreviewArtifacts)` (SSOT in `lib/safeguards.ts`, memoized once per artifact change). The hash is a two-lane 53-bit FNV-style fold over **only** the fields that cross to WASM and change pipeline output — per artifact: `id, slot, set, rank, rarity, level, exactLevel, faction, mainStat.variant, substats[].{variant,isFlat,totalValue,rolls}, equippedChampion.location` — mirroring `toWasmArtifactStoreInput`/`toWasmTestItem`. It deliberately **excludes** display-only / non-projected fields (`lastUseLocalTimestamp` — which bumps every game round — `rerollCount`, `ascension`, `source`, `isLocked`, champion id/name). Consequence: during RSL Helper farming, getting 1–2 artifacts then using/removing them returns the set to a matching-identical state → the *same* cache key → a hit (~0 ms) instead of a full pipeline recompute (~3.9 s on 7755 artifacts). Correctness: an in-flight run writes its result under the hash of the artifacts it actually processed, so it can never be served as a stale hit for a different set; the only remaining clear is on base-HSF change (HSF identity isn't in the content key). On a cache hit the served safeguard detection is shallow-copied with a fresh `scannedAt` (entries are content-identical; only the "last scanned" display time is refreshed — no detection recompute), and `currentMergedRulesHash` is restored from the cached result so the export-dirty badge stays exact across the round-trip. Per-field sensitivity is guarded by `tests/unit/artifact-content-hash.test.ts`.

### SFC dirty flag: provenance decides, not history position

**The contract (SSOT `lib/sfcProvenance.ts`): a document is clean if and only if its current
content exists somewhere the user can get it back from WITHOUT this tab.** Not "unchanged since
load", and not "history index equals savedIndex" — those are mechanisms, and both answer the wrong
question. Recoverability is the question, and every load site already knows its own answer.

Before this, every load path called an unconditional `markNextSnapshotAsSaved()`, so a bundled
preset, a user's `.sfc`, an autosave restore, and an append-import all presented identically as
saved. Three of those four were wrong — an autosave restore in particular has **never** touched
disk, which is exactly the loss the ramp below exists to warn about, yet it cleared the dot and
reset the clock.

`anchorNextSnapshot(provenance)` (renamed from `markNextSnapshotAsSaved`) replaces it. Three values
cover every call site:

| Provenance | Dot on arrival | Call sites |
| --- | --- | --- |
| `anchored` | none (clean) | SFC file/preset load (`App.tsx` `handleSfcFile` path); express **gear-only** silent restore |
| `derived` | dirty, clock starts now | selective/Shift import; clear-all-recipes |
| `recovered` | dirty, clock **resumes** the persisted stamp | autosave restore dialog |

- **`provenanceIsClean`** is the single branch deciding whether a load anchors as saved, so "which
  loads clear the dirty flag" has one definition instead of one per call site.
- **The express gear-only restore is `anchored`, not `recovered`** — it deliberately leaves
  recipes/note/targets alone and dismisses the SFC autosave, so the SFC content is still the
  bundled preset. Only the SFC autosave restore is a recovery.
- **A selective import is always `derived`, even in per-unit "replace" mode**: it merges the chosen
  units into the current document, leaving unselected sections as they were, so the result matches
  no single file on disk.
- **`sfcLoadNonce` carries its provenance** (`{ seq, provenance }`, not a bare counter). The
  post-load safety-net effect force-clears dirty only when `provenanceIsClean` holds. With a bare
  counter, any future derived/recovered path that bumped the nonce would have its dot wiped right
  back off, silently defeating the rule at every call site.
- **`recovered` also drives the staleness clock.** `App.tsx` bumps `sfcRecovery` (`{ seq,
  divergedAt }`), which `useStalenessTracking` turns into `keepStamp` for `resolveDirtySince`. A
  rising edge normally means "a real edit — restart the clock"; a recovery instead adopts the
  divergence stamp, so a document unsaved for hours comes back red rather than as a fresh,
  calm-looking dot. The counter (rather than a boolean) arms the adoption exactly once, so the
  next genuine edit stamps normally. The signal carries its `provenance` and the arming test runs
  it through **`provenanceKeepsStalenessStamp`**, so "which provenance resumes the stamp" keeps one
  definition — the predicate — rather than being re-derived inline from the bare fact that a
  counter moved. A future provenance is then handled by that predicate (and its tests) instead of
  silently falling into the recovery path.
- **The divergence moment travels INSIDE the autosave payload** (`AUTOSAVE_DIVERGED_AT_KEY` =
  `DivergedAt`, stamped by `buildAutosavePayload` from the live `sfcDirtySince`; read back by
  `readAutosaveDivergedAt`). It records when the document first diverged from its last save/load —
  **not** when autosave last wrote, which is the separate `AutosaveSavedAt` the restore dialog
  shows and which bumps on every debounced write.

  It cannot live only in the standalone `stalenessSince` key, because that key is **deleted the
  moment both documents read clean** — so a session that never saved (or any transient clean
  render) destroyed the age before a restore could use it, and the restored dot came back neutral
  no matter how long the work had been unsaved. The divergence moment is a property of *the
  document*, so it is carried with the body it describes and cannot be lost independently of that
  content. On a recovery edge `App.tsx` feeds the body's stamp to `resolveDirtySince` as `current`,
  in preference to whatever the standalone key holds. A missing, malformed, or future-dated value
  reads as `null` ("age unknown") and the edge falls back to stamping now — degrading to the old
  behaviour rather than to a wrong, alarming age. Autosave is ephemeral session state, so entries
  written before the field existed simply take that fallback; no migration is required.

  **`restoreDraft` is an allowlist, so the field must be named there too.**
  `useAutosaveRestore` projects the raw autosave entry into `restoreDraft` by copying named
  fields one at a time — anything not listed is dropped. Writing `DivergedAt` into the payload
  was therefore not enough on its own: the value never reached the restore handler, every
  recovery read "age unknown" and stamped now, and the dot came back neutral no matter how long
  the work had been unsaved. Both ends are pinned by
  `tests/unit/sfc-dirty-provenance.test.ts`; any future field the restore path needs has to be
  added to that projection as well.

  **The recovery stays armed until a rising edge consumes it.** The restore lands across
  **two commits**: `sfcRecovery.seq` bumps first, and `sfcDirty` only flips true once the
  history snapshot for the restored body commits. Disarming on first sight burned the recovery
  on the still-clean render in between, so the real clean→dirty edge saw no recovery and
  stamped now — the dot came back at age 0 and ramped from scratch instead of resuming.
  `useStalenessTracking` therefore only consumes the recovery on the edge that actually uses it
  (`pendingRecovery && sfcDirty && !prevDirty`), which also preserves the one-shot guarantee:
  a later genuine edit still stamps fresh.

**Undo/redo: the saved anchor is clamped across branch truncation** (`clampSavedIndex`, the SSOT
used by both write paths in `useSfcHistory.ts`). Appending after an undo drops
`entries.slice(index + 1)`; the anchor used to be carried across untouched, so an anchor living in
the cut part survived as an index past the end of the array. `index !== savedIndex` was then
permanently true — the document read dirty forever, and undoing back onto genuinely saved content
could never clear it again. Clamping to `null` ("no known-saved entry in this timeline") reads as
dirty while staying reachable by a later save. Undoing back *onto* the anchor still goes clean:
the in-memory document again matches the bytes on disk. Pinned by
`tests/unit/sfc-dirty-provenance.test.ts`.

**The dirty flag is never cleared from a button click.** `HeaderActions`' `handleSfcBeforeOpen`
fires on the Load button's click — the first click only opens the menu (and vetoes the picker
entirely), and later clicks open an OS dialog the user can cancel. The removed `onAboutToOpenSfc`
prop cleared dirty there, so editing → clicking Load → pressing Escape discarded the unsaved-work
signal for a document that had not changed at all. The clear belongs on the load-*completed* paths.

### Staleness ramp (the aging dirty dot)

The app runs from `file://` and therefore can never autosave to disk — the user has to press
**Save SFC** / **Export Sellfile** themselves. A dirty dot that looks identical at five seconds
and five hours gives them no reason to, which is how a user lost a session's work. The dot
therefore encodes *how long* the document has been unsaved.

- **Ramp SSOT** — `lib/stalenessRamp.ts` owns the tier stops, the colour interpolation, and the
  duration split. Stops live in `STALENESS_TIER_MINUTES` (`constants.ts`): **5 / 20 / 60 minutes**
  → `fresh` → `aging` → `stale` → `critical`. The colour interpolates *continuously* between the
  anchors rather than snapping: nobody watches the dot change, they glance at it having changed,
  and a continuous ramp carries "how long" better than four discrete states. `stalenessTier` is
  used only for the discrete behaviours (the critical pulse, the tooltip wording).
- **Anchors are DERIVED, not persisted.** `neutral` = `text.secondary` (the pre-ramp dot),
  `warning` = `warning.main`, `error` = `error.main`. Deliberately *not* four new
  `ThemeCustomization` fields: reading the semantic slots means the ramp retunes itself for free
  under the RSLH preset, a user's custom skin, and — critically — every colour-blind palette,
  since those override `warning`/`error` upstream in `theme.ts`. Unparseable anchors fall back to
  the neutral dot, so a malformed custom theme can only ever restore today's appearance.
- **SFC and HSF age on the same clock**, independently stamped. Saving one leaves the other's dot
  ramping.
- **Only `critical` animates** (a slow 2.4 s pulse), and it yields to `prefers-reduced-motion`. If
  every tier moved, motion would be wallpaper and the one tier that must break through would have
  no escalation left to spend.
- **The dot's geometry is SSOT because an ancestor clips on it.** `DIRTY_BADGE_DOT_SIZE_PX` /
  `_OFFSET_PX` / `_BORDER_PX` / `_CRITICAL_PULSE_SCALE` / `_CRITICAL_PULSE_DURATION_S`
  (`constants.ts`) drive `DirtyBadge`, and `DIRTY_BADGE_OVERHANG_PAD_PX` is **computed from them**
  — resting overhang (offset + border) plus the pulse's `SIZE x (SCALE - 1) / 2` growth plus 1 px
  slack. The header's action row clips horizontally (`overflowX: 'clip'`, so the dot's intentional
  overhang cannot raise a scrollbar in the builder column's scroll box) and pads by that value so
  the dot still paints in full. It previously borrowed `BUILDER_SECTION_GRID_BADGE_PAD_PX`, which
  is documented as sized for the **roll badge's** ~2 px overhang: at 4 px it was already under the
  dot's 5 px resting overhang, so the red pulsing dot — the single state the ramp exists to make
  unmissable — was flat-cut on its right edge. Raising the pulse scale now widens the pad
  automatically instead of silently clipping harder.
- **Colour is never the only carrier.** Past the fresh tier the badge tooltip leads with the
  elapsed span ("Unsaved for 1h 20m — not saved since …"), built by `buildDirtyTooltip`
  (`lib/dateDisplay.ts`). The unit words live in the i18n catalogs (`dirtyBadgeDurationHours` /
  `…Minutes`), so `stalenessDurationParts` returns `{hours, minutes}` rather than a formatted
  string.
- **A restored stamp survives the boot-time clean read.** The app always boots CLEAN (the
  history baseline is established before any edit), so a naive "clean ⇒ clear" rule wiped the
  stamp that had just been reloaded from storage, *before* anything could read it — the dot
  restarted at zero on every reload and could only reach the red tier inside one uninterrupted
  session. `resolveDirtySince` (`lib/stalenessRamp.ts`) is the SSOT edge/restore state machine:
  a one-shot `restorePending` latch lets the first clean observation pass without clearing, so
  only a genuine dirty→clean transition (an actual save) resets the clock. Pinned by
  `tests/unit/staleness-ramp.test.ts`.
- **Edge inputs are snapshotted in the effect body, never read from a ref inside the state
  updater.** A `setState` updater is **deferred**: React may invoke it after the effect body has
  run to completion, so any mutable ref the updater reads has already been overwritten by the
  body's trailing `prevDirtyRef.current = dirty`. Both edge effects originally passed
  `wasDirty: prevDirtyRef.current` from inside the updater, so every rising edge arrived as
  `dirty=true, wasDirty=true` — "still dirty, no edge" — and the stamp was **never set**. The dot
  appeared (it is driven by the dirty flag) but had no age, so it could never leave neutral, and
  the tick never armed either since it is gated on the stamp being non-null. `wasDirty`,
  `restorePending`, the recovery stamp and `now` are therefore all captured as constants before
  `setSfcDirtySince`/`setHsfDirtySince` is called. Pinned by `tests/unit/sfc-dirty-provenance.test.ts`.
- **Clock ownership.** `hooks/useStalenessTracking.ts` stamps the clean→dirty edges, mirrors both
  stamps to `sellfileCreator.stalenessSince.v1` (see
  [Settings & Persistence](settings-and-persistence.md#connection--language--first-run--data)),
  and runs one coarse `STALENESS_TICK_MS` (30 s) interval — only while something is unsaved. The
  `now` it produces is passed *down* to both badges, so every dot ages off one clock and
  `DirtyBadge` stays a pure function of its props (no clock read during render). Edge trackers are
  seeded from the *restored* stamps, not from `false`, so a session that comes back already dirty
  keeps its real age instead of resetting to zero.
- **A recovery edge resumes its stamp instead of restarting the clock.** Accepting the autosave
  restore drives the SFC flag clean→dirty, and a rising edge normally means "a real edit — stamp
  now". That would reset an hours-old unsaved document to a fresh dot at the exact moment the user
  most needs the warning. `useStalenessTracking` therefore takes `sfcRecoveredSeq` and passes
  `keepStamp` to `resolveDirtySince` for that one edge (see
  [provenance](#sfc-dirty-flag-provenance-decides-not-history-position)); with no persisted stamp
  to resume it falls back to stamping now, and the flag never leaks past the restore, so the next
  genuine edit re-stamps normally.

### SFC nudge arrows: the trigger names its target

The bouncing arrow fan (`components/SfcNudgeArrows.tsx`, shared by both buttons) points at
whichever control the user needs next. The target (`SfcNudgeTarget` in `lib/constants.ts`, one of
`'load' | 'save'`) is set by **whoever raises the nudge** — `triggerSfcLoadNudge(target)`, which
defaults to `'load'` — and is carried on the tutorial-coach state as `sfcNudgeTarget`. Only one
nudge is ever active, so the arrows can never point two ways at once.

**It is deliberately NOT derived from `sfcDirty`.** An earlier version used
`sfcDirty ? 'save' : 'load'`, arguing the two nudges were mutually exclusive because "the Load
nudge is only ever raised for a document that is empty or still matches a bundled preset". That
premise is false for three existing triggers: first-run Help dismissal, tutorial close
(`handleTutorialClose`) and tutorial completion all raise the nudge to mean *"load something"*,
and none of them touches the dirty flag — `restoreFromTutorialSnapshot()` restores content, not
save state. So a user who had unsaved work when they opened Help got the onboarding arrows aimed
at **Save**, the opposite of what those call sites intend. Naming the target at the trigger makes
the intent explicit instead of inferring it from an unrelated flag.

Consequences:

- Fresh install, empty document → **Load**; freshly loaded and untouched → **nothing**; an
  **accepted autosave restore → Save**, because the startup nudge below passes `'save'` (a restore
  is `recovered` and therefore lands dirty — see
  [provenance](#sfc-dirty-flag-provenance-decides-not-history-position)).
- **`sfcMatchesPreset` only gates the Load target.** That suppression means "you already have a
  preset loaded, so telling you to load one is redundant" — reasoning that does not transfer to a
  Save nudge, which says "your unsaved work is aging" and is just as true for a document that
  happens to match a preset. It is therefore scoped to `sfcNudgeTarget === 'load'`.
- Besides the existing first-run-Help and tutorial-completion triggers, the nudge also fires
  **once on startup** when the session settles with work still unsaved, skipped while the
  first-run Help is open because dismissing that already fires its own nudge. Without this the
  arrows only ever appeared on first run, so the returning user — precisely the one who loses work
  — was never shown anything.
- **The startup nudge waits for the restore dialog, and reads the settled state.** That dialog is
  what *decides* whether there is unsaved work, so nothing is knowable until it closes: the effect
  is declared after `restoreDlgOpen` and returns early while it is up. It also triggers on the
  **live** `isDirty` rather than a flag frozen at mount from the persisted stamp. Previously it
  could fire while the modal was still covering the screen — pointing the arrows at a button the
  user could not reach — and it pointed at Save even when the user went on to *dismiss* the
  restore, leaving a clean document. Now accepting a restore nudges toward Save and dismissing
  nudges nothing. (The express note-blink waits on the same dialog for the same reason.) It is the
  **only** trigger that passes `'save'`; every other one keeps the `'load'` default.
- **The fan is portalled to `<body>` and `position: fixed`**, anchored to a measured
  `getBoundingClientRect()` of its target (`targetRef`), re-measured on resize/scroll. It is
  deliberately *not* an absolutely-positioned child of the header: the fan hangs ~90 px above the
  button and reaches ~54 px to either side (the ±22° tilt), and the builder column's scroll box
  (`AppLayout/BuilderColumn.tsx`) is `overflowY: auto` — which makes `overflow-x` compute to `auto`
  as well, so an in-flow overflowing child raised **both** a vertical and a horizontal scrollbar
  for the few seconds the nudge was up. Fixed-position descendants are excluded from every
  ancestor's scrollable overflow, so the arrows now paint over anything without moving a scrollbar.

## Behavioral Details

- Safeguard-overrides slider values apply for mixed answers: the resolver read the slider value from `answers[questionId][0]`, but a count card that combines an activation radio with a slider persists `[radioOptionId, sliderValue]` (slider last) — so any user-dragged slider on such a card silently resolved to its `default=` (tier `setval` seeds write slider-only answers, which masked the bug). Both resolution sites (the `$value.TOKEN` cross-slider map and the per-question `$value` binding) now split the stored answer via `buildSafeguardAnswerParts`, the existing SSOT for exactly this shape. Regression coverage: `tests/unit/safeguard-slider-answer-shape.test.ts`.
- Min vs Roll Upper Limit exclusivity: The builder now enforces mutual exclusivity; toggling one clears the other. SFC persists only the active choice (`min`, `max`, or `any`).
- Roll Upper Limit enforcement: Rule generation filters distributions that exceed a per-substat `max`. A `max = 0` enforces “no rolls” on that substat.
- Auto resolution: Auto now keys strictly off `min ≥ 1` across selected substats; star and the Roll Upper Limit are ignored for Auto.
- Rank Any uses 6★ baseline: When `rankCode = 0` (Any), base substat targets map to the 6★ bucket for threshold generation (conservative default).
- Rarity ranges (≥): Conservative lower-bound behavior. `rollLevelsForRarityCode` maps `≥ Common..≥ Epic (6..9)` to the lower bound’s schedule (Common/Uncommon/Rare/Epic), and `≥ Legendary (16)` to Legendary. `rarityIncludesMythical` no longer assumes Mythical for any `≥` range; only exact Mythical (15) and `≤ Mythical (14)` imply the Mythical pre-roll.
- Rarity ranges (≤): Upper-bound schedule behavior. For substat-presence calculation (how many substats exist at each level), `rarity_for_schedule()` in Rust maps `≤ Uncommon..≤ Mythical (10..14)` to their concrete upper-bound rarity before the addition-mask lookup. Previously all LTE codes shared `addition_mask=15` (Common schedule, 4 additions → 0 substats at base), causing `minCount` rules to generate no rows when paired with an LTE rarity.
- Any rarity baseline check: For the “how many substats exist” feasibility pass, `Any` is treated like `≥ Legendary` (no additions). Mythical pre-roll is still not assumed unless Σ mins or aggregate min equals 5.
- Rarity label parsing: SFC normalize accepts human-readable `Rarity` strings (e.g. `"≥ Epic"`, `"Legendary"`, `"Any"`) and maps them to canonical codes. Numeric `rarityCode` is also accepted; `rarityExact` is no longer supported.
- Metaset name resolution on paste: `parseRecipesFromText(text, metasets)` resolves `artifactMetaSetNames` against the caller-provided current metasets. For full SFC objects, `parseSfcObject` resolves names against embedded `Metasets`; if absent, falls back to the app’s current metasets (`prev.metasets`). No default metasets are injected implicitly.
- Per-recipe pruning: Obsolete elimination now runs per recipe before merging, so preview table counts match the builder’s chip count. Builder finalize ordering/pruning now runs in the WASM rule engine before merge-level ordering, while cross-recipe overlaps remain visible for auditability.
- Obsolete comparator: Compares substats by the same StatVariant and raw Value for the same operator (no normalization to rolls). Tie-break prefers earlier rule indices within a recipe when values are equal.

## File Import UX

- Global drop target: The entire app window accepts file drops. Local dropzones were removed to reduce friction. Implemented via `useFileDragDrop` + `FileDragOverlay`.
- Overlay on file drag: A full-screen, non-interactive overlay appears on real file drags, indicating that `.sfc` (legacy `.sfc`, recipes + metasets), `.hsf` (sellfile), and `.db` (gear database) are accepted. Overlay uses `pointer-events: none` so it never blocks the actual drop.
- Routing by extension: Drops are dispatched by filename extension — `.sfc`/`.sfc` → SFC loader (`readSfcFile`), `.hsf` → HSF loader (`readHsfFile`), `.db` → gear importer (`importGearDatabaseFromFile`). Unknown extensions trigger the shared “file format” dialog so users know the payload was rejected.
- Load triggers: The `Load RSL Helper Sellfile` button follows the same flow as drag & drop, so it accepts `.hsf` for base merges and `.db` gear dumps for the Gear Inspector.
- Error handling: Invalid or unreadable files (any of the accepted extensions) route through a single error dialog that spells out the supported formats so failures never disappear silently.
- Safety: Only intercept drags when `DataTransfer.types` includes `Files`; component drags (e.g., table column reorder) are unaffected.
- Load semantics:
  - `.sfc`/`.sfc`: Load/drag replaces the entire state (metasets, substatTargets, recipes, final-sell, selection, note). No conflict merging on file load.
  - `.hsf`: Only the optional base Sellfile is replaced; builder recipes remain untouched so merges stay deterministic.
  - `.db`: Gear rows are queued into the Gear Inspector queue (and the preview auto-switches to the Gear Inspector grid) without forcing the Tools dialog open or mutating builder/export state. Manual/custom tester entries are left untouched so ad-hoc examples survive repeated imports regardless of whether the DB came from drag & drop, the picker, or the CLI command. Invalid DBs surface the same file-format dialog mentioned above.
    - The SQL.js WASM bundle is baked into the release as a data URI (`__SQL_JS_WASM_INLINE__`) so this workflow keeps working even when contributors open `dist/index.html` via `file://` with no dev server.

## SFC Global Note

- Schema: SFC may include an optional root-level `Note: string` with Markdown content.
- Load: When an SFC with `Note` is loaded, a modal dialog opens automatically (view-only). The dialog can also be opened via the always-visible note button in the SFC controls row: `Add Note…` when empty, `Note…` when populated (opens in view mode).
- Auto-open UI: The auto-opened dialog hides the `Edit Note & Dynamic Overrides…` action so editing only happens after the user reopens the note manually.
- Close: The dialog schedules its dismissal on the next animation frame; if a new note opens immediately after a close request (common during SFC imports), the pending close is cancelled so the modal overlay never lingers.
- Edit: The dialog uses an embedded Markdown editor (`@uiw/react-md-editor`) with sanitized previews (`rehype-sanitize`). The editor lives in `src/components/NoteDialog.tsx`.
- Edit toolbar: clicking `Insert Sample Recipe Overrides` opens a scrollable popover (with a close button) showing the recipe overrides EBNF and a compact example; a button inside inserts the sample block at the cursor.
- Edit/View switch: The edit dialog now includes a `View Note…` button (outlined, bottom-left) that switches back to view mode. If any dynamic overrides markers (recipe or safeguard) changed versus the original note, the button shows a warning badge.
- Dynamic overrides actions: When the note contains recipe or safeguard overrides markers, the dialog footer adds `Reset Options to Defaults` (clears all slider and question answers for both systems) plus a toggle that reads `Disable Dynamic Overrides...` (with confirmation) or `Enable Dynamic Overrides`. Disabled state dims both recipe and safeguard override cards and ignores all answers without removing the markers. The confirmation dialog offers `Apply and Disable` (writes the current override answers to stored recipes and safeguard rules before disabling) or `Disable Without Applying`.
  - Recipe overrides DSL: HTML comments inside the note can render interactive question blocks in the read-only view. Markers can be inline or multi-line; whitespace is optional.
  - Marker: `<!-- recipe-overrides ... -->` with exactly one question per comment.
  - Marker options: add `[columns=N]` after `recipe-overrides` to render a card whose answer options flow in a horizontal grid. `N` scales the card to N times the width of a normal card (0 or 1 = standard width), e.g. `<!-- recipe-overrides [columns=2] -->` produces a card as wide as two standard cards side by side.
  - Question header: `q`/`question` plus a quoted prompt: `q "Prompt"`.
  - Groups: `radio`/`rb`/`single` (single-select) and `check`/`cb`/`multi` (multi-select). Each group is `group "Label" ["Text"] [id=TOKEN] [*|default] [constraints] { @selector { assignments } ... }` (the `id` and default markers can appear in any order before constraints).
  - Two-column option labels: when a group uses two strings (label + text), the recipe overrides card switches to a two-column layout; the first string renders as the label column and the second string renders as the value column for every option in that card. In `[columns=N]` layout, the label and text render as two stacked rows, and the checkbox/radio aligns to the first row.
  - Group fallback: add `fallback { ... }` or `else { ... }` inside a group to apply when that group has no selections; multiple group fallbacks stack in source order.
  - Selectors: required `@` blocks. Supported selectors include `@all`, `@tagged`, `@untagged`, `@tag=token`, `@tag in [a,b]`, `@rank>=5`, `@rarity>=epic`, `@minrolls>=2`, `@lockedminrolls>=2`, `@minsubstats=2`, `@flex=on`, `@ignoredbysafeguards=on`, `@reworkgate=reworked|notReworked|any`, and `and`/`or`/`not` (or `&&`/`||`/`!`) expressions. `not` binds tighter than `and`, which binds tighter than `or`.
    - **Behaviour flags**: `ignoredbysafeguards` and `reworkgate` are the two recipe fields that used to be "magic" tags. Both work as conditions *and* assignments, and take `=`/`:` only (a flag is a state, not a magnitude — there is nothing for `>=`/`<=` to order). `ignoredbysafeguards` takes the shared boolean keywords (`on`/`off`/`true`/`false`); `reworkgate` is tri-state and takes `reworked`, `notReworked`, or `any`. As a condition, `reworkgate=any` matches exactly the recipes with **no** gate; as an assignment it **clears** the gate. Both flags OMIT their falsey state on write (`ignoredbysafeguards=off` and `reworkgate=any` delete the field rather than storing it), so a recipe an override merely touched still re-serializes byte-identically. Field-token SSOT: `DSL_FIELD_IGNORED_BY_SAFEGUARDS` / `DSL_FIELD_REWORK_GATE` (`recipeFlags.ts`); accepted gate values: `NOTE_RECIPE_OVERRIDES_REWORK_GATE_VALS` (`noteRecipeOverrides.ts`).
    - **Legacy tag spellings** (read-only, same removal window as the file-load tag transcode): a `@tag=ignore_by_safeguards` / `@tag=if_reworked` / `@tag=if_not_reworked` selector — plus the aliases in the `LEGACY_TAGS_*` constants — still parses, folded onto the equivalent flag condition. **The fold is silent — no diagnostic.** Files inside the legacy version window have their note selectors rewritten at SFC load, so text still spelled the old way *at edit time* was typed by hand and means exactly what the fold makes it mean; there is nothing left to warn about. Warning would also be actively harmful: any diagnostic inside an option drops it to raw-DSL display, so a legacy block — including a shipped preset's own note — would render uneditable even though the parser understood it and would re-serialize it canonically on save. Genuinely unparseable DSL is still rejected as before. Classifier SSOT: `legacyRecipeFlagForTagToken` (`recipeFlags.ts`), which the file-load transcode also routes through, so a spelling can never be recognized in a file but not in a note.
  - Assignments: `field (=|>=|<=) value` pairs. Supported fields: `export` (active/disabled/toggle), `rank`, `rarity` (including `auto`), `lvl` (range or single milestone), `keep` (early/late), `autolate` (uncommon/rare/epic), `minrolls`, `lockedminrolls`, `minsubstats`, `flex`, `ignoredbysafeguards`, `reworkgate`, `substatmin`, `substatmin.<stat>`, `minima.any`, `minima.<star>.<stat>`, and `rolltarget.<stat>` (see below). Five fields take a comma-separated token list: `slots=Weapon,Helmet` (replaces the recipe's artifact-type filter), `substats=SPD,ATK%` (replaces the substat selection), `mainstats=ATK%` (replaces the main-stat selection), `gearsets=` (gear-set selection; bare names replace, `+Name` adds an include, `+-Name` adds an EXCLUDED entry, `-Name` removes the entry), and `metasets=` (metaset display names; `+`/`-` mutate, bare names replace). Values are case-insensitive slot/stat/set names; quote multi-word set names (`"Swift Parry"`).
    - **Clear-to-any**: `gearsets=any` / `metasets=any` empties that filter, which is how HSF spells "any gear set" (no set listed). It exists because there was previously no way to *widen* a filtered rule from an override — only `-Name` removals, which couple the block to every current member name. Keyword SSOT `NOTE_OVERRIDES_CLEAR_LIST_KEYWORD` + `isClearListTokens` (`noteOverridesParser.ts`), honoured by the recipe **and** safeguard parsers; the serializer round-trips an empty replace back to `any` via `emitClearableList`. Only these two fields accept it — every other list field still treats `any` as an unresolvable name (silent no-op). A metaset literally named `any` is shadowed by the keyword.
    - **Quoting trap**: a prefixed multi-word value MUST carry the prefix INSIDE the quotes — `gearsets="+-Divine Speed"`, never `gearsets=+-"Divine Speed"`. The tokenizer does not classify `-` as a symbol, so the latter lexes as the word `-"Divine` followed by `Speed"`: the opening quote never starts a string and the unbalanced quote silently swallows the NEXT option in the marker. `parsePrefixedToken` reads the prefix off the string value, so the correct form round-trips identically and is what `overridesSerializer` emits.
    - **Composition**: list operations matching one rule are folded **in note order**, not last-writer-wins — a later `replace` resets the value, a later `mutate` builds on what earlier ones produced. So two options can each write `gearsets=` on the same recipe and both land (the lategame Chaos Ore fine-tune checkboxes rely on this). The safeguard domain always folded in order; the recipe domain was aligned to it, since silently dropping all but the final write is never the intent.
  - `rolltarget.<stat> = <base>, <+1>, <+2>, …` — Sets absolute roll target thresholds per substat for matched recipes. The first value is the Base (0-roll) threshold; each subsequent value is the absolute threshold at +1 through +5. Trailing values may be omitted — omitted positions use `max(factory, lastSpecified)`, so the threshold never drops below the last explicitly set value. Example: `rolltarget.flat_hp = 300, 600, 900, 1200, 1500, 1500`. A warning badge appears on the Roll Targets heading in the substat flyout when this override is active.
  - Fallback: `fallback { ... }` or `else { ... }` applies when no group has selections.
- IDs + constraints: `id=TOKEN` assigns a stable option token that is global across recipe-overrides markers (first occurrence wins). Constraints are evaluated in this order: `set`/`+` (turn listed options on), `unset`/`-` (turn listed options off), then exclusions (`!`/`excl`) and allow-lists (`only`/`^`). `set` applies first, `unset` can override it, and exclusions/allow-lists resolve afterward. `needs <ids…>` is a UI-only enable-gate (it does not change selection): the option renders disabled/greyed until at least one referenced option is selected — used e.g. so the Chaos Ore "level cap" and "ignore slots" boxes are inert until a rarity is kept. An optional `needs=on|off <ids…>` sets the checkbox's *displayed* state while the gate is unmet (display only — the stored value is untouched and returns when the gate is met again); the Chaos Ore boxes use `needs=off` so they show unchecked while greyed. Explicit IDs scope cross-question behavior to the questions that contain those IDs; numeric tokens stay question-local. If no `id=` is present, the option’s 1-based index is its token and remains scoped to that question.
  - Cross-domain slider writes (`setval`, persist-on-select): a checkbox/radio can set a **slider** (in either overrides domain) at the moment it becomes selected. `setval TOKEN=N [, TOKEN=N…]` writes value `N` into the slider whose `id=TOKEN` matches; a plain `+TOKEN` / `-TOKEN` (or `set`/`unset`) that names a slider id toggles it on (at its default) / off. The write is **persisted** into the slider's stored answer — a real value, exactly as if the user dragged it there — not a render-time overlay. So afterwards the slider is just an ordinary stored answer: changing it is a normal edit (no snap-back, no "release" of the setting option), and selecting a *different* mode simply writes the new values. The directive→write resolution is SSOT in `collectCrossDomainSliderWrites` (`noteRecipeOverrides.ts`), driven by the `id=token → {questionId, defaultNum}` map from `buildSafeguardSliderTokenMap` (`noteSafeguardOverrides.ts`). Two call sites share it: (1) the dialog's recipe answer-change handler (`handleRecipeOverridesAnswerChange` in `NoteDialog.tsx`) diffs the resolved recipe selection before/after the change and applies the directives of every **newly-selected** option; (2) at **SFC/preset LOAD**, `seedSafeguardAnswersFromRecipeDefaults` (called from the load paths in `App.tsx`) applies the directives of the **initially-selected** option(s). The load-time seed is what makes a preset's default-selected mode (the `*` option, which never fires a selection-change event) actually apply its forced slider values — without it the sliders silently fell back to each slider's own `default=`. Seeding never overwrites a safeguard answer that already exists, so an autosave restore or a prior user edit is preserved. A token that names no real slider id is ignored. Example (shipped `lategame.sfc`): every account tier forces both the keep-piece thresholds and the improvement-chance percentages — e.g. the default Lategame carries `setval min_spd_pieces=12 min_debuffer_pieces=24 min_dmgsurv_pieces=24 impr_art=33 impr_acc=33`, so loading the preset seeds those sliders (`id=min_spd_pieces` / `id=min_debuffer_pieces` / `id=min_dmgsurv_pieces` / `id=impr_art` / `id=impr_acc`). The resolved option exposes the directives as `setValueDirectives` (+ raw `setTokens`/`unsetTokens`/`excludedTokens`), which the FORCES section of the option hover tooltip renders as a `setval token=value` row. Malformed `setval` pairs are surfaced as syntax diagnostics: a non-numeric value (`setval x=y`) and a bare target with no `=value` (`setval x`) are both flagged by `collectRecipeOverridesDiagnostics` instead of being silently dropped.
  - Cross-domain **option** writes (persist-on-select, recipe → safeguard): a recipe option's `set`/`+TOKEN` and `unset`/`-TOKEN`/`excl`/`!TOKEN` directives may also name a **safeguard radio/checkbox option's** explicit `id=TOKEN` — `set` selects it, `unset`/`excl` deselect it. The write path mirrors the slider bridge exactly: same two call sites (dialog change handler for newly-selected options; `seedSafeguardAnswersFromRecipeDefaults` at load), same persist-on-select semantics (a real stored answer the user can change afterwards — not a lock), and the seed never overwrites an existing answer. Each affected safeguard question runs through the same rule pass a real click takes (`applyQuestionSgSelectionRules`), so single-select replacement/fallback and in-domain exclusions apply identically, and default-matching results stay implicit (key removed). SSOT: `collectCrossDomainOptionWrites` (`noteRecipeOverrides.ts`) + `buildSafeguardOptionTokenMap` / `applySafeguardOptionWrites` (`noteSafeguardOverrides.ts`). Precedence and limits: a token that names a safeguard **slider** id keeps its slider-toggle meaning (the option bridge only claims tokens the slider map does not know); implicit numeric option tokens stay question-local and never participate; the reverse direction has its own bridge with different firing rules (next bullet). The editor-preview FORCES tooltip shows cross-domain forces too: `NoteOptionInfoTooltipWrap` inverts the both-domain option lookup and merges raw-token resolutions into the on/off/excl rows, so a `set util_off` renders exactly like an in-domain force. The DSL serializer already round-trips the raw `+`/`-`/`excl` tokens verbatim, so the visual override editor preserves cross-domain directives without changes. Example: a recipe option with `set util_off` selects the safeguard option whose `id=util_off`, visibly flipping that card instead of silently overriding its activation. (The shipped `lategame.sfc` no longer uses option writes — its FW-Hard question was deliberately decoupled from the utility card so each domain's cards stand alone — but the bridge remains a supported DSL capability.)
  - **Reverse** cross-domain option writes (safeguard → recipe): a **safeguard** option's `set`/`unset`/`excl` tokens may name a **recipe** option's explicit `id=TOKEN`. Firing rules differ deliberately from the forward bridge: a source option that both deselects X (`excl`/`unset`) and selects Y (`set`) in the same recipe question is a **conditional replace** — it fires only while X is actually selected, applied as a radio switch to Y (preferred), so the group never falls back to its default/first option. A bare `set` is a hard select (skipped when already selected); a bare `unset`/`excl` is an uncheck (skipped when not selected; single-select groups then fall back per the usual default/first rule). Reverse writes are **interactive-only** — fired from the dialog's safeguard answer-change handler (`handleSafeguardOverridesAnswerChange`) for **newly-selected** options, with NO load-time seeding (stored answers are state, not intent). Crucially, a reverse write never re-runs the forward writes of the recipe option it selects — otherwise a downgrade like `Yes!`→`Yes` would immediately stomp the safeguard answer the user just picked (only a real click on the recipe option re-forces its safeguard targets). Storage goes through the same SSOT a real click takes (`applyRecipeOverridesAnswerChange`), so cascade, default-omission, and normalization are identical. SSOT: `collectCrossDomainRecipeOptionWrites` + `buildRecipeOptionTokenMap` + `applyRecipeOptionWrites` (`noteRecipeOverrides.ts`). Example: a safeguard option with `excl fw_yes set fw_yes16` downgrades a recipe radio from `Yes!` to `Yes` the moment it becomes selected — but only for players actually on `Yes!`. (No shipped preset currently uses reverse writes — the lategame FW-Hard ↔ utility coupling that motivated them was later removed in favor of fully independent cards — but the bridge is a supported DSL capability with unit coverage in `reverse-cross-domain-option-writes.test.ts`.)
  - Prompt references: Wrap option labels in backticks to render them as chips (e.g., ``Answering `Yes` will...``). Use numeric references like `` `\1` `` (1-based) to inject the Nth option label. Wrap emphasis text in `**double-asterisks**` to render it with the Quota/Scope label style that inherits the surrounding text size; both markers work in prompts and option labels. Prompts accept literal newlines or `\n` escapes; the first line renders as the title and any remaining lines render as subtext with the same emphasis markers.
  - Multi-select groups can be cleared to zero answers; an explicit empty selection bypasses defaults until the user reselects options.
  - Single-select groups keep exactly one selection: if multiple options become active via `set`, the newest user preference wins when provided; otherwise the first surviving option is kept.
  - Single-select groups auto-pick the first compatible fallback (preferring defaults) when constraints remove the current choice, without cascading into further removals.
  - When constraints conflict, the most recently selected option wins and conflicting selections are cleared before fallbacks apply.
  - Questions are evaluated top-to-bottom; selector blocks apply in the order they appear so overrides resolve deterministically.
- Recipe overrides effects: Answers never mutate SFC recipes. Instead, selector blocks compute effective runtime overrides (export mode, rank, rarity, level window, min rolls/substats, flex, substat mins, and global minima targets) for previews + exports while recipes stay unchanged in storage. Overrides apply only when the selector matches a recipe; otherwise stored values are preserved.
- Global minima overrides: `minima.any` updates the fallback star used for Rank = Any, and `minima.<star>.<stat>` updates the per-star Substat Target table. These overrides are runtime-only and do not persist to SFC/autosave payloads — the computed *effect* is never written into the stored `Minima` table. (The user's override *answers* do persist, so reloading the document reproduces the same effective minima by re-deriving them from the note.)
- Document answers (recipe + safeguard): Override answers are **document state** — they only mean anything against the Note that declares the questions — so they are written into the SFC payload immediately after `Note`, under the same three keys autosave has always used: `NoteRecipeOverridesAnswers`, `NoteSafeguardOverridesAnswers`, and `NoteRecipeOverridesDisabled` (the disabled flag keeps its legacy key name for backward-compatible restore). One writer (`buildSfcPayload`) and one reader (`parseSfcObject`) now serve the `.sfc` file, the localStorage autosave, and the background account push — the autosave payload is a superset of the readable SFC schema, so it inherits the fields for free. `App.tsx` no longer spreads the keys onto the autosave payload by hand, `useAutosaveRestore` no longer digs them out of the raw record, and `backgroundAccountPush` reads them off the parsed document.
  - Empty maps emit **no keys at all**, so documents without overrides stay byte-identical to what earlier versions wrote.
  - **Default-equal safeguard answers are dropped before that empty check** (`dropDefaultSafeguardOverridesAnswers`, `noteRecipeOverrides.ts`), so an *untouched* document emits nothing even when the note seeds answers. This matters because the effective default is **not** each slider's `default=`: a recipe option selected by default (the `*` account tier in `lategame.sfc`) forces sliders through cross-domain `setval`, and those forced values are the real baseline — comparing against `default=` would keep all six and every save of an untouched preset would carry a full answer map. The baseline is `seedSafeguardAnswersFromRecipeDefaults(note, recipeAnswers)`, which is idempotent and a fixed point, and it is computed against **the document's own recipe answers** so a non-default tier is compared with *its* forces (Endgame's values are omitted under Endgame but kept under Lategame). Safe because the import path re-derives the same baseline, so an omitted default is reconstructed identically while a genuine deviation survives alongside its default-valued siblings. Pinned by `tests/unit/sfc-overrides-empty-omission.test.ts`.
    > Do **not** "fix" this by aligning the preset's slider `default=` with its `setval` and deleting the directive: `tests/unit/lategame-preset-overrides.test.ts` enforces that *every* account tier forces the full slider set, and that a fresh load seeds the forced values rather than the slider defaults. Suppression belongs in the writer, not the preset.
    > **The lean-write contract is enforced at the resolver seam, not per call site.** `buildDocumentOverridesView` seeds internally before resolving, so *every* consumer of a document — the app, autosave restore, and `backgroundAccountPush` — re-derives the same baseline. That matters because the background push feeds a parsed document straight in with no seeding of its own; without this an untouched Lategame preset resolved `count=16/32` there while the app showed `12/24`, i.e. the pushed sellfile kept materially more gear. Seeding never overwrites an existing answer and is a fixed point, so pre-seeded callers pass through unchanged.
  - On load, `parseSfcObject` returns `null` for an absent key — deliberately distinct from `{}` (present but empty). That distinction is what lets a legacy file fall back to seeding the note's authored defaults while a file that deliberately stores no answers keeps none.
  - The answers are a **lean** map: only the user's deviations are stored, matching the autosave model (the named-preset library in `dynamicOverridesPresetsPreference.ts` uses the *full resolved* snapshot instead — the two models are intentionally different). A question the user never touched therefore follows the note's *current* default, so an updated preset's improved defaults still reach the user.
  - Load path: `applyNoteChange(..., { mode: 'import', importedRecipeAnswers, importedSafeguardAnswers })` is the SSOT. Import mode adopts the document's stored answers, pruning them against the note that actually arrived, then runs `seedSafeguardAnswersFromRecipeDefaults` — seeding never overwrites an answer that already exists, so cross-domain slider forces still fire for questions the file did not answer. With no stored answers it degrades exactly to the previous reset+seed behavior. Callers must NOT reset the answer maps after this call; it runs last in the batch and would be clobbered.
  - `sfcPresetMatch.canonicalize` deliberately passes no answers, so override state never affects preset-identity comparison.
  - **Copy All Recipes** carries the answers *and* the disabled flag, and paste applies both when it adopts the note (`adoptPastedNote` in `useSfcClipboard.ts`) — matching file load and shift-load, so a document copied with overrides switched off does not paste them back on. That copy already includes the whole Note (plus metasets, targets and safeguards), so copying the note while leaving its configuration behind would paste a preset that silently reverts to the DSL defaults. Paste still only overwrites the note when the current one is empty, and the pasted answers are pruned against whichever note ends up active.
  - **Preset patches** can pin the shipped answers via `noteRecipeOverridesAnswers` / `noteSafeguardOverridesAnswers` / `noteRecipeOverridesDisabled` (`lib/presetPatch.ts`, documented in `presets/PATCHES.md`). Whole-value replace; omitted leaves the base preset untouched; an explicit `{}` means "ship with no answers". That module is deliberately dependency-free, so it re-declares the three wire key names locally — `tests/unit/preset-patch.test.ts` compares them against the app's exported constants so a rename fails loudly instead of producing presets the loader ignores.
- Safeguard overrides DSL: HTML comments `<!-- safeguard-overrides ... -->` render interactive question blocks that override SafeguardRule fields at session time, mirroring the recipe overrides structure but targeting safeguard properties.
  - Marker and layout: `<!-- safeguard-overrides [columns=N] -->` with the same `[columns=N]` width hint as recipe overrides. One question per comment.
  - Question, group, constraint, and `id=TOKEN` syntax are shared with recipe overrides (same underlying parser).
  - Selectors: only tag-based selectors apply — `@all`, `@tag=token`, `@tag in [a,b]`, `@tagged` / `@untagged`, and `@grouped` / `@ungrouped` (group membership, the analogue of tagged/untagged — see [Groups](#groups-safeguards-sharing-one-required-count)). All combine with `and` / `or` / `not` and parentheses. Recipe-only selectors (`@rank`, `@rarity`, `@minrolls`, etc.) have no meaning here, and `grouped`/`ungrouped` conversely have none in a recipe block (a recipe is never part of a group).
  - Assignment fields: `activation` (off / protect_existing / anticipate_gaps / anticipate_improvements), `count` (arithmetic expression; see below), `ignprev` / `igncoll` / `ignvault` (boolean — ignore previous safeguards / equipped-in-collection / equipped-in-vault), `perfaction` / `permainstat` / `perslot` / `perset` / `perrule` (countMode booleans), `substats` (comma-separated stat names, replaces substat selection), `substatmatch` (1 / 2 / 3 / 4 / persubstat), `weight.<statKey>` (numeric substat weight), `improvchance` (disabled / off / `$value` / one to four numeric thresholds 0–100 for levels 0, 4, 8, 12). `$value` (or `$count`) binds the enclosing slider's position as a flat threshold across all four level stages — used to drive the feature from a slider instead of radio options. Combination-filter lists mirror the recipe DSL's prefix syntax (`+` add / `-` remove / all-bare = replace): `rank=` (integers 1–6), `rarity=` (integers or names), `faction=` (names or ids), `gearsets=` (set names editing `combination.sets`; `+-Name` adds an EXCLUDED entry — the syntax the lategame FW-Hard question uses to strip Daze from the utility rules), and `metasets=` (metaset display names editing `combination.metaSetNames`). Both accept the **clear-to-any** keyword (`gearsets=any` / `metasets=any`) documented under the recipe DSL above — the lategame catch-all scope question uses `metasets=any` to widen those rules to every gear set. The prefix parser (`parsePrefixedToken`/`classifyListMode`/`isClearListTokens`/`consumeCommaSeparatedRemainder`) and the set-name→id map (`artifactSetIdByName`) are single definitions shared with the recipe parser, and cross-domain `safeguard @tag=… { … }` blocks inside recipe options accept the same fields (one `parseOperations`).
  - Group fields (`group.*`): `group.count` and `group.perfaction` / `group.permainstat` / `group.perslot` / `group.perset` / `group.perrule` retune the GROUP a matched rule belongs to, never the rule itself. The distinction mirrors the builder: a member's own `count` sizes what it FEEDS its group, while `group.count` is what the group KEEPS out of the merged pool, bucketed by the `group.per*` chips. `group.count` accepts the same arithmetic/`$value` grammar as `count` (same parse helper, same slider resolution, and the same visual calc widget in the block editor), so a slider can drive what the group keeps — e.g. `count=$value group.count=$value/2`. On an ungrouped rule every `group.*` assignment is ignored (there is no group to retune). Because a run's members must all carry identical group settings, matching ANY member writes the whole run — and two stretches sharing an id but separated by another entry are two runs, only the matched one being written.
  - Count arithmetic: the `count` field accepts full arithmetic expressions using `+`, `-`, `*`, `/`, parentheses, unary minus, and the special tokens `$value` / `$count` (the enclosing slider's current value). Cross-slider references use `$value.TOKEN` where `TOKEN` matches another slider's `id=`. The final result is rounded and clamped to [1, 9999].
  - Slider params: `min` / `max` / `step` / `default` (numbers) define the range. `marks=<value>:"label"[:"subtext"],…` adds labeled guide ticks (visual only — the slider stays continuous, no snapping); the optional subtext is shown as a hover tooltip on that mark. `unit="%"` appends a display-only suffix to the slider's shown value and drag tooltip (the stored answer stays the bare number). `toggle="label"` adds an on/off checkbox bound to the slider; when unchecked the slider's `else { … }` block applies (e.g. `improvchance=disabled`) and the track is disabled. `toggleside=left|above` (default `above`) places the checkbox inline-left of, or stacked above, the slider; `toggledefault=on|off` (default `on`) sets its initial state. When `toggleside=left`, the checkbox is rendered inside the slider's own centred row so it shares the track's centre line (mark labels hang below the whole row, not just the track).
  - Enumerated-value validation: every closed-set assignment/param value is checked against its accepted set and an unrecognized value is flagged by the error checker (via the SSOT helper `reportInvalidEnumValue`) rather than silently falling back to a default. This covers `toggleside`/`toggledefault` and slider toggles, `needs=on|off`, recipe `export`/`keep`/`autolate`/`flex`, safeguard `activation`/`substatmatch`, and every boolean field (`ignprev`, the `per*` chips and their `group.per*` twins). (Numeric/range/id fields keep their existing structural diagnostics.)
  - Unknown-field validation: a field the grammar has no branch for is **skipped by the parser** (so a note written by a newer app version still applies its other overrides here) but **underlined by the editor** — one `reportUnknownField` diagnostic anchored on the field token. This covers plain typos (`notafield=3`) and bad dotted suffixes (`weight.spdd`, `group.perslots`). The skipped value is consumed up to the next assignment, so a bad field never swallows the ones after it. Both halves come from the same parse; the editor's diagnostics collector is the only difference (see [note-overrides-editor.md](note-overrides-editor.md#lenient-parse-strict-editor--the-diagnostics-contract)).
  - Operation ordering: within a question's selector blocks, assignments apply in source order and the last matching block wins for each field per rule. This lets a single slider control both primary and fallback rules: list the primary-tag operation first and the fallback-tag operation last so rules tagged with both always receive the fallback value.
  - Effects: overrides never mutate stored SafeguardRules. `applySafeguardOverrides` produces an effective rule set used by the pipeline and display; stored rules are only changed when the user explicitly chooses `Apply and Disable`.
  - **Chip edits must not bake overrides in.** `SafeguardChipsPanel` renders `displaySafeguardRules` (stored rules + overrides applied) but commits to the *stored* rules, so it hands `onRulesChange` an **updater**, never an array derived from its `rules` prop. Resolving an edit against the display list and committing that array replaced the whole stored document with its override-applied form — grouping two chips wrote the overridden values onto every rule including the ones not selected, "Save .sfc" then persisted them as the user's own, and the (i) badges vanished because the stored values now equalled the effective ones. Index-based edits are safe on either list because overrides rewrite a rule's *fields*, never the list's shape; `applySafeguardRulesChange` applies the updater to the real stored state. The same read-display/write-stored split is why `handleSelectSafeguardRule` loads the builder draft from `safeguardRules`, and why the panel's **clipboard** actions (copy rule / copy selected / copy all) read a separate `storedRules` prop instead of `rules`: a payload is persistable user data, so serializing the display form would let a paste write the overridden values back as the copy's own. Rule of thumb: `rules` is for rendering only — anything that ends up committed *or* on the clipboard comes from the stored list. Pinned by `tests/unit/safeguard-chip-edits-vs-overrides.test.ts`.
  - Document answers: safeguard override slider and question answers persist into the SFC payload alongside the recipe ones — see "Document answers (recipe + safeguard)" above for the shared write/read path. Disabling dynamic overrides suppresses both recipe and safeguard override parsing simultaneously, and that disabled flag is saved with the document too.
  - (i) badges: When a safeguard override is active, affected fields in the Safeguard Builder Panel show an (i) badge whose tooltip displays the stored value → effective value transition. The Sets select carries ONE badge covering both `gearsets=` and `metasets=` overrides (the two fields feed the same combined control); its stored/effective labels come from the shared `formatArtifactSetSelectionLabel` (metaset names first, set names after, excluded entries prefixed `–`) — the same formatter the recipe builder's sets badge uses.
- **Card text is not markdown.** Question prompts and option labels render through `buildQuestionPromptTokens`, which scans for exactly two markers: a backtick (chip styling) and a double asterisk (label styling). Single-asterisk `*italics*` match neither and render their asterisks literally — use ```chips``` or `**labels**` instead. The surrounding note PROSE does go through the real markdown pipeline, so italics are correct there; the split is easy to trip over when moving a sentence between the two. Pinned by a test in `lategame-gearset-scope.test.ts` that scans marker bodies for single-asterisk runs.
- Inline gear-set icon token: `{set:Name}` renders the set's icon plus its localized name anywhere in the note — in question prompts, in option labels, and in the surrounding prose. Names resolve case-insensitively and tolerate padding (`{set: swift parry }`); an unresolvable name degrades to the bare name rather than vanishing, and a malformed token (no closing brace, empty/whitespace name) survives verbatim so an author never loses text. Spelling mirrors the `{buff:…}`/`{debuff:…}` convention already used by `setDescriptions`. Names are **localized at render time** via `getLocalizedGearSetName(setId, t)`: the parsed segment carries the id plus the canonical English name only, so a note never freezes to whichever language was active when it was parsed. Two gotchas the wiring depends on: (1) react-markdown's `allowElement` gate accepts only alphanumeric tag names plus an explicit whitelist, so `note-set-icon` must be listed there or every PROSE icon is silently dropped while override-card icons keep working; (2) the token is inline markup, so it can appear inside `**bold**` and ```code``` — every branch of `renderQuestionTextTokens` (chip, label, plain) must route through the splitter, not just the plain one. SSOT: `noteSetIconToken.ts` (`NOTE_SET_ICON_TOKEN_KEYWORD`, `splitNoteSetIconSegments`, `stripNoteSetIconTokens`), consumed by BOTH render paths — the `NoteSetIconRuns` component inside the prompt/label tokenizer, and the `rehypeSetIconTokens` pass that rewrites prose text nodes into `note-set-icon` elements before sanitize (`<code>`/`<pre>` subtrees are skipped so a documented literal stays literal). Option-label width measurement strips tokens first, or a `{set:Speed}` label would reserve 11ch for a 5ch word. **Alignment**: the run is an inline-flex box using `alignItems: baseline` + `verticalAlign: baseline` (SSOT `NOTE_SET_ICON_RUN_SX`), so the set NAME sits on the surrounding text baseline; `center`/`middle` centre the box on the line instead and push every name 0.09–2px off the text around it. The icon is a flex item (its own `verticalAlign` is inert there) and is nudged onto the x-height by `NOTE_SET_ICON_IMAGE_SX`. Pinned by a Playwright test that measures name-vs-preceding-text baselines and requires < 0.05px, comparing only pairs that share a line box (a wrapped run legitimately sits a line-height lower).
- Metasets table marker: `<!-- metasets -->` renders the file's metasets as a live two-column table in the note view (`MetasetsNoteBlock`: glyph + name | member sets as icon + localized name; `show: false` metasets render dimmed). The table always reflects the CURRENT metasets — renames, membership edits, and additions appear immediately. The note editor's `Insert Metaset List` toolbar button inserts this marker (it previously pasted a static bullet-list snapshot that went stale). Marker keyword SSOT: `NOTE_METASETS_MARKER_KEYWORD` (`metasets.ts`); the whole-comment regex cannot collide with the overrides DSL's `metasets=` assignment field, which only occurs inside overrides markers.
- Note localization: a Note authored in one `.sfc` can carry per-language text for both the interactive override DSL and the surrounding prose, falling back to English when the active app language has no translation. Two complementary primitives, both pure string transforms keyed on the active language, both routing their language pick through one SSOT resolver (`pickLocaleFromMap` in `noteOverridesParser.ts`) so precedence can never diverge:
  - Inline DSL segments (`[[xx]]`): inside any quoted DSL string (`q`/`cb`/`rb`/`single`/option label/detail, slider `unit`/`toggle`/`marks`), `[[xx]]` (BCP-47-ish: `de`, `pt-BR`) starts a per-language segment running to the next `[[…]]` or end-of-string. The text **before** the first tag is the English base, and it alone is the canonical identity source — `questionId` and `option.id` derive from the base (`dslLocaleBase`), so adding or removing translations never shifts a stable id (saved answers and cross-question `id=` refs survive a language switch). Display localizes at the resolve boundary (`localizeDslDisplay(raw, lang)`); the parser stays language-agnostic. Resolution order: exact full code (`de-DE`) → bare language prefix (`de`; for `pt-BR`, `pt-BR` beats a generic `pt`) → English base.
  - Block-level prose groups (`<!-- lang -->…<!-- /lang -->`): for whole markdown regions (paragraphs, headings, colored/`data-blink` spans). A *group* is bracketed by `<!-- lang -->` (English base text follows) and `<!-- /lang -->`; inside, each `<!-- lang:xx -->` marker starts a localized variant running to the next variant marker or to the close. At render time exactly one slice survives — the active language (same exact→prefix order) or, when none matches, the whole base. The explicit brackets make the group the fallback unit: a region falls back to its base **together** and never interleaves languages. Resolved by `localizeNoteProse(note, lang)` at the `renderNote` boundary in `NoteDialog`, **before** markdown + override-marker parsing — so the override/conditional markers (`recipe-overrides`, `safeguard-overrides`, `dungeon-simulator`, `if-no-endpoint`) and their signatures are untouched by language. Only the read-only view localizes; the editor still shows (and saves) the raw multi-language source, so persisted Note data is never rewritten by a language switch. Markers are plain HTML comments, so legacy renderers degrade to base + every variant shown inline (untranslated, harmless).
- Save/Copy: If a Note exists (non-empty), SFC exports and “Copy All Recipes” include it.
- Paste semantics: Pasting SFC content (via context menu or manual paste) only overwrites the current note if the current note is empty. Loading a file always overwrites the current note.
- Metaset conflicts on paste (Copy/Paste only): identical value (same sets) keeps current ID and remaps pasted references. If the same ID has different sets, a single dialog offers: Keep current, Use pasted, or Keep both (new ID for pasted). Unknown pasted metaset IDs create hidden placeholders with generated names so chips never show raw IDs.
- Dependencies: `@uiw/react-md-editor`, `@uiw/react-markdown-preview`, and `rehype-sanitize`.

## Gear Inspector

- Purpose: Gear editing lives in the Tools dialog Gear tab (open via the `Gear…` button next to the preview toggle); it lets users build “what if” gear, paste manual stats, or import `.db` files without leaving the builder. The Gear Inspector (the grid on the main screen) consumes that shared queue to evaluate which rule would keep or sell each artifact under “first match wins”.
- Surfaces: The Sellfile Preview header exposes two related controls:
- `Gear Inspector` preview toggle — switches the main preview between the default HSF rule rows and the gear grid (this toggle is what “Gear Inspector mode” refers to).
- In Gear Inspector mode, the preview header chip shows the keep/sell/safeguard outcome summary (total, sold, kept, safeguard) instead of the item-count label; when filters are active each metric renders as filtered/total.
- The Gear Inspector grid defaults to grouping artifacts by set and accessories by faction + set. The Sort popover exposes separate **Artifacts** toggles (`Set`, `Slot`, plus a shared `No headers`) and **Accessories** toggles (`Faction`, `Set`, `Slot`, plus the same `No headers`). Toggles are combinable; when enabled, grouping always nests in the fixed order (`Set → Slot` for artifacts, `Faction → Set → Slot` for accessories), and the order of clicks does not matter. When no grouping toggles are enabled, artifacts/accessories fall back to single flat sections with headers. `No headers` suppresses all accordions and renders a single flat list; a compact "Gear" header strip is always shown above the grid in this mode (see selection controls below). Grouping applies even when no sort priorities are selected; when substat sorting is active, non-default grouping still uses a single global sort order instead of re-sorting inside each section. Each card dedicates three columns to the schematic preview (slot glyph + set badge + overlays), the main/substat stack, and the matching-recipe summary (keep/sell glyph, primary rule/recipe chip, plus additional matching recipes capped with a `+N` chip). Virtualization runs at both the group and card level so collapsed groups skip rendering and large inventories stay responsive.
- Sort priorities include both stat variants and synthetic keys (`Last Used`, `Newest`, `Improvement Chance`, `Safeguard Rank`); `Newest` orders by artifact id (higher id first when using the default descending direction). `Safeguard Rank` sorts by the best (lowest-numbered) candidate rank across active safeguard rules — rank #1 first, unranked items last; requires safeguard detection to have run and produces a no-op sort when no rank data is available.
- Card hydration runs through a reveal queue that flushes within a ~6 ms frame budget, prioritizes on-screen cards, prunes entries more than ~4,000 px away whenever the queue passes roughly 70 items, and drains the backlog whenever scrolling pauses for ~200 ms; rows that fall outside the window simply re-enqueue when the user scrolls back toward them, which keeps reverse scrolling responsive without throwing away recent warm-up work.
- Right-click anywhere inside the Gear Inspector grid scroll container opens the grid context menu (hinted via `useContextMenuHint('gearInspectorGridContextMenu')`). The menu mirrors the preview header controls: toggle stat-color text + Manage Colors, cycle the color-blind palette, flip between `4`/`5` column layouts (default `4` at >= `sm`, and the button text simply shows the active number), show/hide the first-match and other-match rows, optionally display champion portraits for vault/collection gear, and toggle keep/sell background emphasis (green tint for keep, red tint for sell, enabled by default). The `Show Substat Rating` row also acts as a quick preset-toggle shortcut: clicking the row hides all enabled rating presets, and clicking again restores the last non-empty preset selection (first-run fallback: presets `1` through `6`). A `Safeguard Rank` cycle button toggles the safeguard rank chip overlay through four modes (key `GEAR_INSPECTOR_GRID_SHOW_SAFEGUARD_RANK_KEY`, default `off`): `off` → `bucketRank` (group) → `rank` (safeguard) → `both` — the canonical order + button labels live in `src/lib/safeguardRankCycleOptions.ts`. The chip only appears when safeguard detection has produced rank data. The chip text, tooltip rows, and tooltip title all reflect the active mode: `bucketRank` shows `#group`, `rank` shows `#safeguard`, `both` shows `#group · #safeguard` (group first). Tooltip rows are sorted by the displayed rank (bucket rank when shown, else safeguard rank); the chip mirrors the top (best-ranked) row — its number, green/red colour (that rule's keep/sell verdict within its group), dim state, and click target all refer to that one rule, so they never disagree. Clicking either overlay chip (improvement-chance `%` or safeguard rank) when the chip carries a rule ordinal opens the Safeguards editor and scrolls to the associated rule (`openLogicHubSafeguardRule`); the click never triggers card selection because `GridIconBox` stops propagation before invoking the chip callback. These preferences persist through `src/state/gearInspectorGridPreferences.ts` and `src/state/gearInspectorGridNormalizedOverlayPreferences.ts`, so grid layout and overlay choices survive reloads.
- Each Gear Inspector card can show a gear action button (main Gear Inspector grid only) that opens `Create Keep Recipe` / `Create Sell Recipe`. The button is hidden by default and can be enabled via the Gear Inspector grid context menu. The actions insert a new recipe after the current selection (or append when none is selected) and focus it in the builder. Default template logic is documented in `technical/gear-inspector-rule-templates.md`.
- When the RSL Helper WebSocket endpoint is active, gear cards become selectable. Selection model: **plain click** is always additive (adds the card, updates the shift anchor); **Ctrl/Cmd+click** removes the card from the selection (updates anchor); **Shift+click** adds the range from the anchor to the clicked card; **Shift+Ctrl/Cmd+click** removes that range (anchor unchanged in both shift variants). Each accordion group header shows two icon buttons (`Select all in group` / `Unselect all in group`) that operate on the group's entire subtree — these stop event propagation so they never toggle the accordion. In `No headers` mode, a "Gear" header strip above the grid carries the same global controls plus a live count of selected items; this strip is always present regardless of endpoint state so the layout stays consistent. Every selection change immediately sends a `selectArtifacts` JSON-RPC request (see [WebSocket Protocol](../../userDocs/websocket-jsonrpc.md#selectartifacts)) with the full set of selected artifact ids. The update is fire-and-forget — the UI reflects the new selection immediately and never reverts it based on the server response; if the server needs to override, it should push a correction event. Selected cards show a primary-color border tint and background highlight. Selection is cleared when the endpoint goes offline.
- Champion portraits: when a gear entry references a champion (imported collection or vault gear) and the “Show champion icons” preference is enabled, the card swaps the slot glyph for the champion image. Collection items show only the portrait, while vault items add the vault glyph to the right of the portrait, aligned under the gear’s level badge. If no known portrait exists (or the preference is off) the card reverts to the original slot glyph + source icon combo so the grid never loses the origin indicator.
- Fresh sessions start empty — no sample gear is auto-added. Import RSL Helper DB dumps, paste gear, or add custom items via the dialog to populate the grid.
- Ctrl/Cmd+clicking a top-level accordion header (artifact set or faction) collapses/expands every group at once, while the same gesture on a faction’s set accordion only affects that faction’s sets. A normal click still toggles just the targeted accordion.
- `Gear...` button — opens the Tools dialog on the Gear tab where gear can be edited, pasted, or imported; edits are reflected immediately in the preview toggle mode without reopening the dialog.
- The Gear tab only renders custom entries; imported inventory/equipped/inbox rows stay visible in the preview and can be batch-deleted per-source via the new toolbar buttons. A persistent `Add custom gear` action lives in the tab footer so users can rebuild lists from an empty state.
- Custom-gear safeguard item-key (`getSafeguardItemKey`) resolves by the ladder `artifact.id (>0) → previewExtras.id → gearInspectorItem.itemId → 0`. Two defects made distinct custom pieces share one key — collapsing the substat-weight flyout onto one piece's substats and dropping its hover tooltip:
  - **Duplicate copied identity (primary cause of the reported bug).** `cloneManualGearInspectorItem` copied `previewExtras` verbatim, including `previewExtras.id` — the highest-precedence key. Duplicating a piece therefore produced clones that all resolved to the *source's* item-key despite each getting a fresh `itemId`. Fix: the clone now drops `previewExtras.id` **and** `equippedChampion` (both are identity, not shape) so each duplicate is keyed by its own `itemId`.
  - **Low custom ids collided with DB ids.** `itemId` was allocated ascending from 1, sharing the positive-integer space with real DB artifact ids (up to ~264 k across example DBs). Custom ids are now allocated **descending from `INT32_MAX`** (reserved band ≥ `2^30`); the sentinel/floor, `isGearInspectorCustomItemId`, `nextGearInspectorCustomItemId`, and `reseedGearInspectorCustomIdCursor` are SSOT in `src/lib/itemIdentity.ts`. `buildPreviewArtifactFromGearInspectorItem` surfaces an in-band `itemId` as a **positive** `artifact.id` so the ladder returns it directly. `deserializeGearInspectorItems` migrates legacy autosave: any `itemId` that is missing/duplicate/out-of-band is relocated into a fresh descending id on load, so pre-existing sessions self-heal.
- Custom-gear substat editor (Tools → Gear): every slot-valid substat stays selectable in each row's dropdown. Picking a stat already used by another slot **swaps the two rows** — because `subValues` is keyed by variant, swapping the two positions in `subOrder` moves each stat *with its own value*, so reordering never clears a slot first or loses data.
- Preview toggle persistence: The Sellfile Preview / Gear Inspector mode toggle saves its last selection to `localStorage` (defaulting to Sellfile Preview) so reloading the app restores the same table.
- Preview scroll retention: Sellfile Preview and Gear Inspector each keep their own scroll offset when switching modes; if filtering or row removal shortens the content, browser clamping keeps the restored position within bounds.
- Rule-source chips: Final Sell matches render a warning-colored `Final Sell` chip, and Safeguard matches render a green `Safeguards` chip; both cases bypass the regular HSF rule label so the Gear Inspector grid immediately calls out the special keep path.
- Recipes flagged `ignoredBySafeguards` still appear in the other-match list, but Safeguard becomes the first match when those recipes are the only keep sources.
- When a Safeguard rule is the primary match, the other-match row shows every matching recipe instead of dropping the first recipe entry.
- Toggling either recipe behaviour flag forces a rule-cache rebuild so Gear Inspector matches update immediately. This is automatic: both are real `BuilderRecipe` fields, so `recipeSnapshot.ts`'s generic key sweep folds them into the cache fingerprint with no registry to keep in step.
- Last-used filter: the Gear Inspector filter drawer adds a `Last used` section with quick presets (`Never used`, `≤7d`, `≤30d`, `≤90d`, `>90d`) plus an “Advanced range…” popover for custom day ranges. Presets act as toggles that combine as a union (only one `≤N` bucket remains at a time so redundant mixes like `≤90d` + `≤30d` collapse), and the custom slider also unions with the presets so users can mix precise ranges with the coarse buckets. Timestamp-free gear is controlled entirely by the `Never used` preset—there is no longer a custom “include unknown” switch—and the active state still contributes to the global “filters on” indicator.
- Gear Inspector fingerprinting includes `lastUseLocalTimestamp`, so DB delta updates that only change last-used metadata still invalidate the cache and refresh the grid.
- Gear Inspector cards surface everything inline: slot glyph + rarity-bordered frame with `8px` corners, overlapping rank/ascension stars, 16px keep/sell + reroll glyphs, level badges, set badge tooltip (includes the set bonus stats), main stat + ascension rendered inline in 4-column mode (the ascension line drops below the main stat in the tighter 5-column layout), substats with glyph deltas/roll badges and Mythical underline, the matching rule/recipe chip (button jumps to the builder rule for normal recipes, but opens the Tools dialog → Safeguards and focuses that card when the match source is a safeguard), and a single-line row of additional matching recipes capped with a `+N` chip. Source/faction info remains below the icon stack, matching the Sellfile preview cues, and leaf accordions add padding so edge cards do not clip the borders.
- The row below the icon stack now renders source glyph chips instead of text so the inventory/vault/collection distinction is clearer. Manual entries use the build glyph, collection rows use `PersonOutline`, the vault glyph reuses the inventory icon, inbox items keep `MailOutline`, and inventory entries render the tooltip/aria label without a glyph. The Source chip line is driven by `src/lib/gearInspectorPreviewFormatting.ts` + `SOURCE_ICON_MAP` in `src/components/GearInspectorItemsGrid.tsx`, and the tooltips still show translated labels for screen readers.
- Preview sorting: Gear Inspector cards sort artifact pieces before accessories, then by set (in-game numeric order), slot (`compareArtifactTypes`), rank (6★→1★), rarity (Mythical→Common), ascension tier (highest first), level milestone (16→0), and main-stat priority so custom gear stays grouped predictably with game metadata.
- Rules source: Evaluates against the effective rules array provided by the preview (merged base + custom when present). Disabled rules never match.
- Match freeze: `suppressGearInspectorMatchDetails` hides the imported gear whenever we rebuild matches so the grid only renders steady-state results. Autosave restores that also rehydrate recipes/metasets keep a single freeze alive across both queue passes (initial rehydration plus the rules-triggered rebuild) by tracking the final Gear Inspector build id; users now see one hidden → match transition after everything commits instead of two quick flashes. While a freeze is active both the preview grid and Safeguards dialog pass `suppressMatchDetails` to `GearInspectorItemsGrid`, which now leaves the first/other match rows visible but dims the chips + outcome badge and disables their jump handlers so users remember the previous match without accidentally drilling into stale data.
- Evaluator: `src/lib/ruleEval.ts` exposes `evaluateFirst(rules, item)` (pure). Uses shared rank/rarity coverage helpers from `src/lib/hsfTypes.ts`.
- Autosave: Session persists under `AUTOSAVE_GEAR_INSPECTOR_KEY`, stores the gear list as a gzip/base64 payload (plus a saved timestamp), and is offered as an optional checkbox inside the global Restore dialog. The queue only replaces the current Gear Inspector state when the user selects the checkbox; otherwise the saved copy remains in storage until they opt in or overwrite it with a newer autosave. Autosave activates automatically once the gear deviates from the initial baseline (imports, restores, edits) and stays active even if the Gear tab is closed; opening the Tools dialog also primes autosave immediately.
- Gear resets (`Reset to defaults → Gear`) route through the same `beginGearInspectorMatchReset('gearDbManual')` helper as DB imports so the Gear Inspector match worker cancels in-flight builds, clears Safeguard detection, and emits a fresh snapshot before the grid re-renders an empty queue.
- State ownership: `App.tsx` holds the gear list via the helpers in `src/lib/gearInspectorSession.ts`; the dialog receives `[items, setItems]` plus the shared row-id allocator so edits flow directly into the preview without extra effects.
- Gear entry shape (readable summary):
  - Slot (`ArtifactTypeId`), Set (`ArtifactSetId`), Rank (`1..6`), Rarity (`1..6` Common..Mythical), Level (`LevelMilestone` entries 0/4/8/12/16), Faction (`FactionId` for accessories), Main (`StatVariant`), Substats as absolute values (variant→value) preserving user order.
- The count of available substats derives from rarity and level; values clamp to per-rank substat targets from the shared `SubstatTargetTable`. Substats equal to the selected main or not allowed by slot are filtered out. Missing substats are auto-filled from allowed candidates up to that availability count.
- Sentinel IDs: `ACCESSORY_NO_SET_ID = -99` means “None — Only accessories” and is shared by the Gear Inspector and Final Sell remainder; `TESTER_ANY_SLOT_ID = 0` means “Any slot” and only matches rules that do not restrict slots.
- Set selectors surface the accessory-only “No Gear-Set” entry when accessory slots are in scope. In game/icon ordering it is pinned immediately before `Refresh`; in A–Z ordering it follows normal alphabetical sorting. Filters, Builder, Safeguards, Metasets, and the Gear dialog all allow selecting it when accessories are included; Final Sell explicit-set rules emit the same `-99` id for coverage.
- Sets dropdown: each gear entry owns its menu state (`setsMenuOpenIdx`); only the active card’s `Select` is forced open, and the menu anchor is cleared on the next animation frame after close. This keeps artifact/accessory filtering intact, closes immediately after choosing a set (including the accessory “No set” sentinel), and prevents the anchored menu from jumping horizontally when reopening the selector.
- Compact summary chips always render accessory faction icons with a tooltip so the Gear Inspector snapshot mirrors the Sellfile Preview; the global “Factions as icons” preference does not hide them.
- The combined rule/recipe chip displays the recipe faction icon (when set) under the same preference, matching the Sellfile Preview header behavior.
- Constants: Layout sizing is centralized in `src/lib/constants.ts` (`TESTER_*` widths and heights, result row minimum height) to keep the dialog compact and stable across locales.
