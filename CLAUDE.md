# Claude Code Guidelines

This document summarizes how we collaborate on Sellfile Creator. Detailed technical references live in [`docs/TECHNICAL.md`](docs/TECHNICAL.md); that index links to (and may contain) additional guidance beyond the highlights mentioned here.

## Objectives

- Deliver a reliable, minimal app for generating RSL Helper sell files.
- Keep scope tight — ship the requested behavior without speculative add-ons.
- Prefer clarity, safety, and testability over shortcuts.

## Working Agreements

- TypeScript-first with strict types; avoid `any` unless the type system cannot describe the value. Reuse exported domain enums/tokens (see `docs/technical/rules-and-data.md`).
- Maintain dense, purposeful inline documentation—new or updated code should average a short comment every 2–3 lines to explain intent, not mechanics.
- Single source of truth / One Definition Rule is a hard gate: every shared literal, behavior, or logic expression must have exactly one exported definition — import it everywhere else. Writing the same condition or computation in a second place, even inline, is the same violation as duplicating a constant; extract a named function first.
- **Color/theme is held to the same SSOT+DRY gate.** No inline `rgba(...)` / `alpha(x, 0.n)` magic numbers or hardcoded hex in components — fixed-alpha tints come from `colorTints` (`TINT`), JS alphas from `ALPHA`, per-scheme alphas from `theme.custom.*`, and colour math/contrast from `colorUtils`. User/preset colours rendered as text must be contrast-adapted to the runtime scheme (`useSubstatFgAdapter` / `adaptSubstatFg*` / `resolveRarityTextColor`). When you spot anything that doesn't match — an inline alpha, a raw user colour used as text, a theme colour inside an easter egg, a duplicate/near-duplicate value — consolidate it, unless it is one of the valid exceptions documented in [`docs/technical/theming-system.md`](docs/technical/theming-system.md#color-ssot--tints-alphas-and-contrast-adaptation). When merging a value, gimmicks (easter eggs, psychedelic mode, chart dance animations) defer to regular features/controls — their exact alpha is unimportant, so pick the value that gives the regular feature the best UX/contrast.
- Comments and docs must reflect the *current* state. Update or remove anything that has drifted, even if the surrounding code was not otherwise touched.
- When adding console debug output to help diagnose an issue alongside the user, log formatted primitives (e.g. ``console.log(`[builder-count] pending=${pendingId}`)``) instead of passing raw objects — DevTools collapses objects and they do not copy usefully into chat.
- Cap files at roughly 1,500 lines; split large modules (without breaking SSOT) before they become unwieldy.
- **i18n catalog edits — use double-quoted strings**: Catalog values use TypeScript double-quoted strings (`"..."`). This eliminates the Unicode apostrophe trap — U+2019 (`'`) in languages like Ukrainian is harmless inside double quotes. When adding new entries, use double quotes for values. If a value contains a literal `"`, escape it as `\"`.
- Keep modules focused and diffs small. Follow existing patterns before introducing new abstractions, unless doing so would violate the single-source-of-truth / One Definition Rule—then factor the shared abstraction instead of duplicating logic.
- UI code must keep parallel entry points in sync (e.g., toggles, badges, multi-edit). Shared helpers exist for a reason — extend them, don't fork them.
- **Agent auto-memory is per-clone; clones/branches are disposable.** Never store project-specific knowledge (architecture, fixes, gotchas, perf numbers, workflows) in your agent auto-memory — other checkouts and agents will never see it. Project knowledge belongs in the repo: put it in the appropriate `docs/technical/*.md` file (create one and link it from `docs/TECHNICAL.md` if needed). Auto-memory may only hold project-*unspecific* facts (user preferences, machine/tooling quirks that apply beyond this repo). If your auto-memory contains project-specific entries, migrate them into the docs and delete them from memory during your current session — this rule is the trigger; don't wait to be asked.

## Workflow Expectations

- Propose a brief plan before sizable changes and update it as work progresses.
- When a prompt is ambiguous, summarize your understanding and ask the user to confirm before proceeding.
- For code changes, always run `npm run typecheck`, `npm run lint`, `npm run build`, and `npm run test:unit` before handoff. Also run e2e when the change touches flows covered by e2e specs — while iterating use **`npx playwright test --project=chromium-fhd`** (functional specs only). Do **not** routinely run `npm run test:e2e:chromium`: it chains `--project=chromium-perf --workers=1` after the functional pass, which adds many minutes of timing-sensitive benchmarks that say nothing about a behavior change. Save the perf project for release gates (`release:win` runs it via `test:all`). Fix regressions instead of punting them downstream. (`npm run release:win` runs `npm ci` to sync `node_modules` to the committed lockfile, then gates on `npm run test:all`; `npm run release:win-dev` skips both for fast iteration.)
- **Never extend a timeout to fix a slow or flaky test.** A longer timeout makes no correct test faster and fixes no broken one — it only makes the failure slower, and reflexive bumping has cost this project hours of dead waiting. When a test is slow/flaky, diagnose the *wait* (wrong target; a `waitFor({ state: 'visible' })` that blocks its full budget when the spinner is missed; a real perf regression) before touching any budget. For Playwright: budgets are named tokens in `tests/playwright/timeouts.ts` (no raw numeric `test.setTimeout` literals — lint-enforced), preview-pipeline settling goes through `settleWorkload()`, and visible-waits stay on the short `expectDefault` budget. Full rules live in the "Timeout policy" section of [`docs/TECHNICAL.md`](docs/TECHNICAL.md). If you believe a budget genuinely must grow, stop and get explicit user confirmation, with the per-iteration math that justifies it.
- Remove exploratory logs, diagnostics, and scaffolding once the fix is validated. If a commit is requested while any remain, pause and obtain explicit user confirmation before proceeding.
- Do not wait for confirmation when run without interactive UI, e.g. if run as commandline prompt in a script.
- Before committing, review earlier iterations and drop any obsolete changes that no longer apply after corrective prompts.
- Update docs when behavior, datasets, or workflows change. Add or edit entries in `docs/TECHNICAL.md` (and create new referenced files when needed) without waiting for an explicit user request.
- **User-facing docs live in `userDocs/` — and only there.** `README.md` + `README.<lang>.md` (Help dialog + shipped text), `HISTORY.md` (release history), the generated `THIRD_PARTY_NOTICES.txt`, and `websocket-jsonrpc.md` (integrator protocol contract). Two hard rules for every file in that folder: (1) **plain language** — write for a player/integrator, short and practical, game vocabulary, no jargon, no AI-sounding phrasing; (2) **describe behavior, never implementation** — players and integrators read these, so no file paths, module/function/hook/test names, script names, constants or build details; a link to the public repository (`https://github.com/Nusi42/SellfileCreator`) is fine. Everything developer-facing stays in `docs/`. The release zip layout is unchanged by the folder (docs flatten to the archive root as `.txt`, the protocol doc goes to `dev/`); see [`docs/TECHNICAL.md`](docs/TECHNICAL.md#user-facing-docs-userdocs).
- Treat the git history as immutable unless the user tells you otherwise. You **must not** stage, commit, amend, revert, or otherwise write to the repository unless the current prompt explicitly authorizes that exact action. A past "please commit" does **not** carry forward; if the user wants additional commits they will say so. When in doubt, ask—never assume permission. The lone exception is when you are dispatched by an orchestration script that sets the `CLAUDE_AUTOMATION` environment variable; those runs already include explicit commit instructions inside the plan, so you may follow the plan's commit/rename steps without asking the user again; their commit messages follow the rules below like any other.
- **Commit messages are Conventional Commits written for a public history** (enforced by the `commit-msg` hook and `npm run check:commit-msg`; rules in `scripts/tooling/lib/commit-message.mjs`):
  - Subject `<type>(<scope>): <subject>`: imperative, lowercase start, no trailing period, at most 72 characters. Types: feat, fix, perf, refactor, test, docs, build, ci, chore, style, revert. Merge commits read `Merge <what it brought>`.
  - Body: what changed and why, in plain English, after a blank line.
  - The only trailer is `Co-Authored-By: Claude <model> <noreply@anthropic.com>`. Never add `Claude-Session:` lines or any claude.ai link.
  - Never mention local checkouts or branch logistics, planning jargon (waves, work packages, milestone codes), the acronyms SSOT / ODR / DRY (describe the change instead), people's roles ("owner"), sessions, notes, or "WIP".
  - Notes-only commits are `chore(notes): …`; better, fold note updates into the work commit.
- **Private data never enters the repository or its history.** The maintainer's private details live in a list outside the repository (`%USERPROFILE%\.sfc-private\patterns.txt`, or `$SFC_PRIVATE_PATTERNS`); the tracked hooks in `.githooks/` (installed by `npm install` via `prepare`) and `npm run check:private` refuse matches in files, file names, messages, identities and pushed commits, and refuse `originSessionId:` lines. Never copy values from that list anywhere, never bypass a hook with `--no-verify`, and report findings masked. Commits are authored and committed as `Nusi42 <167581605+Nusi42@users.noreply.github.com>`.
- Never imply that code edits or commits are expected unless the user has explicitly asked for them in the current prompt.
- Playwright runs may need elevated permissions to let Vite bind `127.0.0.1:<port>`; rerun the shell command with `with_escalated_permissions: true` plus a one-line `justification` describing the port bind whenever the harness responds with `EPERM`. The port defaults to a value derived from the repo path (hashed into `5180–5279`) so parallel clones (e.g. WSL + Windows) get distinct preview ports automatically. Set `PLAYWRIGHT_PORT` to override on the rare hash collision.

## Safety & Data

- Align exports with the sample `.hsf` files under `docs/orig/`; do not guess at schema changes.
- SFC serialization format must remain backward-compatible. Never change a persisted field name or drop a field without a migration path that loads existing saved files correctly. Autosave is ephemeral session state and does not carry this requirement.
- Never silently discard user data. Unknown or unrecognized fields in SFC payloads should be preserved or explicitly warned about — not dropped without trace.
- Avoid destructive commands (mass deletes, force resets) unless the user explicitly requests them.
- Request elevated permissions before taking privileged filesystem or network actions.

Stay concise, keep users informed, and prefer incremental, well-tested changes.
